Governed Work, Effects, Lineage & Reconstructability

Uma única história causal da necessidade original até settlement e aprendizado, cruzando Workflow, Reliability, Identity e Information Survival sem colapsar seus boundaries.

1. Tese consolidada

A unidade estável não é o agent, o prompt ou o process attempt: é o trabalho governado e sua lineage. Demand explica por que algo existe; Work/Workflow representa progressão; ExecutionBinding/attempt identifica quem tentou; logical effect representa mudança pretendida no mundo; reconciliation reduz incerteza; Evidence/Outcome/Settlement fecham claims distintos.
Raw Intake → Grounded Demand → Admission → Durable Work
 → Workflow revision → Route/Binding → Attempt
 → Logical Effect → Observation/Reconciliation → EffectReceipt
 → Validation → OutcomeEvidence → Settlement
 → Attribution → qualified learning/evolution

2. Por que essa cadeia precisa ser contínua

Os estudos históricos tratavam requirements, backlog, workflow, runtime, audit e memory em documentos separados. A pesquisa de 12/08 mostra um risco comum: semantic fragmentation. Se cada subsystem inventa seus próprios IDs, timestamps, actor labels e terminal states, joins posteriores tornam-se ambíguos, audit fica frágil e learning recebe experiências mal atribuídas.

Canonical lineage não significa um Identity Plane. Significa referências estáveis e relações temporais suficientes para perguntar: “qual necessidade originou este work?”, “qual revision estava ativa?”, “qual Permit autorizou o attempt?”, “qual effect ocorreu?”, “qual evidence sustenta o outcome?” e “qual experiência é elegível para aprendizado?”.

3. Work e Workflow: progressão, não agent graph

Workflow deve representar progressão de trabalho heterogêneo: código determinístico, agents, capabilities, humans, waits, approvals e subworkflows. A distinção mais útil da pesquisa é:

  • Template/procedure — estrutura reutilizável;
  • compiled/revisioned instance — plano concreto para o work atual;
  • trace — o que realmente aconteceu.

Graph mutation sem revision identity é rejeitada. Replanning deve voltar pelos paths normais de Authority/Routing. Trajectories recorrentes podem gerar procedure candidates, mas apenas relações de dependência demonstradas viram hard edges; o restante permanece adaptativo.

4. Reliability: attempt não é effect e timeout não é fracasso

Partial failure é o caso normal quando o sistema toca o mundo externo. O cliente pode perder a resposta depois do commit, um observer pode estar stale, cancellation pode disputar com commit e compensation pode falhar. Por isso “exactly once” não deve ser promessa de transporte para efeitos arbitrários.

Princípio: construir one logical effect sobre identidade durável + idempotency/dedup/conditional commit quando disponíveis + reconciliation antes de retry.

Estados úteis incluem `UNKNOWN/AMBIGUOUS → RECONCILE`, sem transformar toda operação numa nova state machine global. Authority freshness também é separada de Permit histórico: um Permit pode ter sido válido quando emitido e ainda assim não autorizar um commit tardio após revogação/supersession.

5. Information Survival e Reconstructive Closure

“Manter tudo no Git” não é assurance. A pergunta correta é quais fatos/relações são irreversíveis e quais projections podem ser reconstruídas. Reconstructive Closure é a capacidade de materializar um sistema operacionalmente equivalente para uma Project revision a partir de seed/inputs declarados — diferente de bit-for-bit reproducibility.

Isso produz quatro classes práticas: fatos canônicos/decisões duráveis; evidence payloads; projections reconstruíveis; scratch/ephemera. O storage backend pode variar. A semântica de reconstrução não pode depender dele.

7. Programa experimental decisivo

  1. Effect Torture Lab: commit-then-drop, drop-before-commit, delayed commit, duplicate delivery, stale observer, cancel/commit race, stale owner e failed compensation.
  2. Workflow conformance: mesma frozen work identity executada pelo incumbent e por um adapter/compiled path; comparar outcome, effects, recovery e cost-to-trust.
  3. Reconstructive Torture Lab: materializar uma Project revision em ambiente limpo usando apenas inputs declarados; medir dependências ocultas e golden-query preservation.
  4. Settlement/reopen: provar que terminal Task não apaga obrigação parcialmente satisfeita e que reopen preserva história.
