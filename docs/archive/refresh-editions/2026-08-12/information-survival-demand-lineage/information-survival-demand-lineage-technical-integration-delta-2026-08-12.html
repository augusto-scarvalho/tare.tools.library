Implementation research delta · v0.19

Information Survival & Reconstructable Assurance — Technical Integration Delta

Delta técnico pequeno, query-first e anti-drift para reconciliar o novo research pack com contratos canônicos antes de qualquer Implementation Packet.

CROSS-LINEAGECORPUS INTEGRATIONNO CANONICAL PROMOTION

1. Status e non-goals

PROPOSED / IMPLEMENTATION RESEARCH. Não implementar diretamente.

Non-goals: não criar Information/Repository Plane; não mover toda state para um database; não acoplar ArtifactRef a OCI; não event-source everything; não tornar OTel/OpenLineage proof authority; não alterar Task/Workflow implicitamente.

3. Golden queries antes de primitives

Can a Project revision be reconstructed from declared seed + inputs?
Which hidden/private/derived inputs are required?
Why does this Work exist and which demand revision caused it?
Is terminal execution also settled demand?
Which evidence became stale after artifact/source drift?
Which decisions/promotions consumed that evidence?
Can designated lineage/evidence queries survive compaction?
Can a foreign projection be removed without semantic loss?

Somente uma resposta ambígua persistente após composição dos contratos existentes cria candidato de ADR gap.

4. Read-only views

Primeira fase: Repository Boundary Inventory, Reconstructive Closure report, Context Reconstruction View, Evidence Recall query pack e Settlement view. Todos rebuildable/read-only; nenhum concede Authority.

5. Integração com Canonical Lineage v0.18

O v0.18 perguntou se a lineage canônica consegue responder “quem/qual Work/Authority/effect/evidence produziu isto?”. O v0.19 adiciona “o que precisa sobreviver para continuar respondendo isso depois de scrub, crash, rebuild, migration, compaction ou upstream drift?”. Assim, Information Survival estende Canonical Lineage; não a substitui.

6. Evidence Recall e reuse

Separar duas operações:

  • Recall: localizar downstream dependents afetados por mudança/revogação/freshness.
  • Reuse: decidir se evidence histórica continua admissível para um claim atual.

Mesmo EvidenceReuseCandidateKey não autoriza reuse sem freshness, revocation e environment equivalence.

7. Reconstructive Closure qualification

Experimentar em Clean Project Seed, não no checkout dirty como única evidência. Medir hidden inputs, time-to-reconstruct, semantic equivalence, Windows fidelity e independent reproducibility. Bit reproducibility é nível separado, não requisito universal.

8. Demand / Task revision / settlement

Não criar Demand ainda. Primeiro modelar queries: origem verbatim, clarification/disposition, revision delta, current scope, residual obligation, settlement owner e reopening trigger. Se Task/Workflow atuais não preservarem a semântica necessária, registrar gap no bounded context proprietário.

9. Technology adapters

OCI/ORAS, OpenLineage, OTel, SLSA/in-toto, Temporal/Restate/DBOS e MLflow ficam em rings de mechanics/projection/lab. Aplicar semantic exit test e qualification pack; remover tecnologia não pode destruir a capacidade do tare interpretar Task/Authority/Effect/Evidence.

11. Candidate BDDs / gates

  • session loss does not lose durable Work/demand provenance;
  • derived projection deletion is recoverable from declared inputs;
  • upstream artifact drift makes dependent evidence stale/unprovable without rewriting historical verdict;
  • terminal execution with unmet demand is not settled;
  • candidate cannot control independent verifier interpretation;
  • Windows clean reconstruction matches required semantic behavior;
  • removing OTel/OpenLineage projection loses observability only, not canonical meaning;
  • private→distribution policy conflict fails closed.

12. Rollback e authority

Todos os slices iniciais são observe-only/shadow e podem ser removidos sem migration irreversível. Stable incumbent continua fallback. Research, derived views e external adapters possuem zero promotion authority.
