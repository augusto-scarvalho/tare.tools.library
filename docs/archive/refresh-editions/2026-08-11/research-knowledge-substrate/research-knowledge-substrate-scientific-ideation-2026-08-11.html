Research Knowledge Substrate: Scientific Organization, Provenance and Enrichment

A scientific and exploratory refinement for turning tare.tools.research into a machine-actionable, human-explorable, evidence-preserving research substrate without creating a parallel authority system.

Positioning. This is RESEARCH and PROPOSED enrichment architecture for the private companion repository tare.tools.research. 1. Problem and objective

The repository has already evolved from an archive into a bilingual, versioned scientific corpus with document lineage, cross-lineage influence, source families and curated refresh editions. The next limitation is granularity: most meaning still lives at document-level. A document can cite fifty sources, contain competing claims, preserve obsolete assumptions and support several bounded contexts simultaneously. A single edge such as SUPPORTS(document A, document B) therefore carries too much ambiguity.

The objective of this round is to make the corpus more machine-actionable without turning it into a heavyweight ontology project or allowing inferred knowledge to become architectural authority.

2. External research patterns worth borrowing

Research Objects

RO-Crate packages files together with contextual metadata and uses JSON-LD/Schema.org as an interoperable representation. This strongly matches our need to bind historical source, translation, editorial edition, refresh, proposal, manifests and provenance while preserving each byte-level artifact independently.

Provenance

PROV-O separates entities, activities and agents. PAV and adjacent approaches further distinguish authoring, contribution, curation and representation. Our current sidecars can evolve into a more explicit provenance projection without changing the canonical storage model.

Version relations

DataCite already standardizes relations such as IsNewVersionOf, IsVersionOf, IsTranslationOf and variant-form relations. Reusing these semantics reduces the amount of tare-specific vocabulary needed for ordinary scholarly lineage.

Citation intent

CiTO demonstrates that a citation is not a single undifferentiated edge: it may support, extend, use a method, critique or otherwise relate to another work. This is directly relevant to our new influence graph.

Machine-actionable contributions

ORKG represents research contributions rather than relying only on document text, enabling structured comparisons over problems, methods and results. This supports introducing claim/contribution views above immutable documents.

Claim-level evidence

Micropublications and nanopublications treat small assertions as citable/provenanced units. PaperTrail's 2026 work reinforces why claim-evidence mapping is useful but also warns that granular provenance can impose cognitive cost if the user experience is not carefully designed.

3. Proposed layered model

Layer 0  Immutable bytes / Git / hashes
Layer 1  Research Object identity
Layer 2  Work / source identity resolution
Layer 3  Version / translation / derivative lineage
Layer 4  Concepts, topics and applicability
Layer 5  Claims, methods, findings and evidence links
Layer 6  Influence / argument / contradiction graph
Layer 7  Temporal validity and curation events
Layer 8  Retrieval, embeddings and graph projections
Layer 9  Human/agent views, dashboards and context capsules
Layer 10 Promotion boundary to canonical tare.tools

The key design principle is that upper layers are rebuildable enrichments over lower layers. A source document can survive even if every classifier, embedding and inferred relation is deleted and recomputed.

4. Research Object instead of loose document

A Research Object should be repo-local metadata, not a kernel primitive. It groups representations of the same intellectual object without merging them:

{
  "research_object_id": "tro:workflow-governed-work:2026-08-11",
  "historical_sources": [...],
  "translations": [...],
  "editorial_editions": [...],
  "refresh_editions": [...],
  "technical_proposals": [...],
  "manifests": [...],
  "external_identifiers": [...]
}

The design is inspired by RO-Crate/FDO but can remain ordinary JSON in CURRENT tooling. JSON-LD should initially be an export/projection, not a mandatory internal dependency.

5. Separate Work identity from Artifact identity

The same scholarly work may appear as an arXiv preprint, accepted manuscript, journal version, author copy, translated edition, HTML mirror or citation entry. Conversely, two similar titles may be different works. We should model:

ScholarlyWork
  ├── WorkIdentity
  ├── External IDs (DOI / arXiv / OpenAlex / S2 / ...)
  └── Manifestations / Versions
       └── concrete ArtifactRef + content hash

For source code, a Git URL alone is insufficient identity. When relevant, Git commit/tree hashes and Software Heritage identifiers can provide stronger content-level references.

6. Claim–Evidence Graph

This is the largest proposed enrichment. Instead of interpreting documents as indivisible truth units, represent selected high-value claims:

Claim C-104
  text: "staged scenario enumeration is HEAD-set based"
  subject: Validation candidate tree
  status: OBSERVED / HISTORICAL
  applicability: repo state + epoch + component
  asserted_by: document / experiment / handoff
  evidence:
    - exact source location
    - command/output or experiment
  relations:
    - SUPPORTS C-088
    - FALSIFIES C-091
    - CONSTRAINS P-014

Only selected claims should be extracted initially. Bulk automatic claim extraction would create enormous curation debt and false precision.

7. Granular source anchoring

Every important claim should be able to point not merely to a document, but to a stable target inside it. A Web-Annotation-like representation can use line ranges, headings, HTML fragment IDs, text selectors or Git blob+line coordinates. This gives us source location provenance while allowing annotations to remain separate from immutable source bytes.

9. Temporal and epistemic state

One timestamp is insufficient. We should distinguish at least:

published_at       when the source appeared
observed_at        when tare.tools discovered it
retrieved_at       when this representation was fetched
valid_from/to      if a claim/policy applies to a bounded period
last_verified_at   latest identity/status check
superseded_at      when a newer work/version became preferred
retracted_at       if formally retracted
curated_at         when a human/agent accepted a relation

A future bitemporal view can answer both: “what do we currently believe?” and “what did the project know on date X?”.

10. External enrichment as receipts, not silent mutation

Crossref, DataCite, OpenAIRE and Semantic Scholar are valuable for metadata enrichment, citation discovery and candidate recommendations, but responses must not silently rewrite canonical research metadata. Proposed pattern:

EnrichmentRequest
  provider + query + requested fields
        ↓
raw response artifact + hash
        ↓
EnrichmentReceipt
  observed_at / provider / response_hash
        ↓
normalized candidates
        ↓
AUTO_ACCEPT deterministic identity facts
or CURATION_REQUIRED semantic relations

This mirrors the tare.tools principle: external systems produce claims/evidence; they do not mint authority.

11. Discovery graph ≠ evidence graph

Recommendations and similarity should live in a separate projection. Semantic Scholar recommendations, embedding similarity, keyword overlap or co-citation can nominate candidates, but must never directly create SUPPORTS, FALSIFIES or SAME_WORK. Suggested relationship states:

DISCOVERED → CANDIDATE → VERIFIED → CURATED
                     ↘ REJECTED

12. Cognitive interoperability and views

Machine-actionability is not enough. The corpus should expose semantic units humans can navigate without reading the raw graph. Proposed views:

  • Document view
  • Lineage view
  • Claim/evidence view
  • Controversy / contradiction view
  • Concept / bounded-context view
  • Timeline / architecture-epoch view
  • Downstream impact view
  • Source-family view
  • Authority boundary view

The FAIREr line of research on cognitive interoperability is a useful reminder that graph structure should improve human explorability, not only machine processing.

13. Active curation and Value of Information

Instead of curating everything uniformly, the system can estimate curation priority from uncertainty and downstream impact:

priority ≈ impact_if_wrong
         × uncertainty
         × downstream_dependents
         × freshness_risk
         × authority_proximity

This suggests a curation queue containing unresolved source identities, claims relying on one evidence family, untyped high-centrality edges, stale external versions, conflicting claims and architecture-adjacent findings.

14. Knowledge-health metrics

Identity health

unresolved IDs, duplicate work candidates, orphan manifestations, stale URLs.

Evidence health

claims with no evidence, single-family support, contradictory evidence, stale verification.

Graph health

untyped edges, low-confidence high-impact edges, disconnected documents, cycles where forbidden.

Curation health

age of review queue, rejected auto-suggestions, relation precision sample, human review burden.

Centrality, citation count and graph density must never be treated as evidence quality. They are prioritization signals only.

This keeps Git as source of truth while allowing multiple specialized projections.

16. Ideas intentionally not adopted yet

  • No mandatory RDF triplestore. JSON/JSONL + generated JSON-LD can deliver most interoperability benefits first.
  • No full OWL ontology of tare.tools research. Start with SKOS-like controlled concepts and typed edges.
  • No automatic claim extraction across all 93 historical files. Pilot on high-value refreshed lineages.
  • No autonomous merge/dedup. Strong IDs may auto-resolve; fuzzy identity remains reviewable.
  • No vector database as truth. Embeddings are disposable retrieval projections.
  • No automatic research→architecture promotion. The existing authority boundary remains intact.

18. Experimental program

  1. Identity pilot: resolve 58 current external source nodes against DOI/arXiv/Crossref/S2 and measure duplicate-resolution precision.
  2. Claim pilot: extract 5–10 high-value claims from each of two lineages, then compare document-level versus claim-level impact analysis.
  3. Anchor robustness: compare line-based, heading-based and text-selector annotations across editorial regeneration.
  4. CiTO mapping: map current influence vocabulary to CiTO; quantify genuinely tare-specific relations.
  5. RO-Crate export: generate a crate for one lineage without changing canonical storage; test round-trip metadata fidelity.
  6. Active curation: rank the current identity-review queue by uncertainty × downstream impact and compare with manual prioritization.
  7. Retrieval: compare keyword, graph-neighborhood, embeddings and hybrid retrieval for known research questions.
  8. Human UX: measure time-to-verify a claim using current document navigation versus claim/evidence view.

19. Future research pointers
