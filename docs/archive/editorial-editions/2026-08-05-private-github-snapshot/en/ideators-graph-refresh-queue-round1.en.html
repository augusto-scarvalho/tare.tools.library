Lens 1 — diagnosis soundness

Summary. Diagnosis is largely sound: the 2s/302s/120s measurements establish a blocking post-commit subprocess as the proximate cause, and the headMoved=True+escalated forensics establish a real correctness divergence. Two gaps remain: the causal bridge from 'git commit timed out at 120s' to 'orchestrator rolled back against an already-committed tree' is asserted not shown, and the shards-as-trigger claim is plausible but not isolated from the key-rotation confound. The unverified key hypothesis is correctly quarantined and is not load-bearing for the fix's correctness.

  1. [medium] Causal bridge from commit-timeout to rollback-against-committed-tree is asserted, not evidenced
    • evidence: forensic-report: 'Command [...] timed out after 120 seconds' (the spy output) forensic-report: 'rt6-committed — outcome=escalated shaMatch=False headMoved=True' forensic-report: 'The orchestrator, having timed out at 120s, recorded escalated and moved to its rollback path — against a repository that had already committed.' plan §1: 'The orchestrator saw a 120s timeout, reported escalated, and proceeded to roll back against a tree that had already committed.'
    • recommendation: The evidence shows (a) git commit timed out at 120s and (b) HEAD moved and the orchestrator recorded escalated+shaMatch=False. It does NOT show the rollback actually executed against the moved HEAD, nor that the 120s timeout was the orchestrator's route_loop budget (vs. a different caller). The design should state the exact failure sequence: which caller invoked git commit, what its timeout was, what it did on TimeoutExpired, and whether rollback ran or was itself guarded. Without this, 'correctness divergence' rests on an inference. Ask the owner for the route_loop log line that triggered rollback, or narrow the claim to 'reported failure after success' which the evidence does support.
  2. [medium] Shards-as-trigger-not-cause is plausible but not isolated from the key-rotation confound
    • evidence: forensic-report: 'Before the flip, ROOT was the real root... Since the flip each shard is a disposable detached worktree pinned to HEAD, whose index is EMPTY — so the guard sees nothing staged, does not fire, and rt6 runs.' forensic-report: 'gate_parallel.py already documents a neighbouring symptom... a spurious self-SKIP; this is a spurious self-RUN — the same blind spot, opposite direction.' forensic-report: 'Unverified hypothesis... the owner rotated every vendor key into the OS vault earlier the same day... That would explain why this fires today rather than since 2026-07-21.'
    • recommendation: The shard argument explains why rt6's dirty-surface guard stopped firing (empty index in a worktree). It does NOT explain why the blocking discover call takes 302s today specifically. The key-rotation hypothesis is the competing explanation for the timing: pre-rotation discover refused fast (no usable key), so even a spurious self-RUN would not have blocked. The forensic report itself notes the guard's purpose is to prevent rt6 running a write-chain during a commit in flight — but the measured 302s is a post-commit discover, which is a different path. The design should separate two claims: (1) shards exposed rt6's guard blind spot (supported by the gate_parallel.py neighbour note) and (2) shards exposed the post-commit blocking (NOT isolated from key rotation). The fix is correct regardless, but the 'trigger not cause' framing overstates what was shown.
  3. [low] The 120s budget attribution to route_loop._default_commit_stage:420 is a code reference the reviewer cannot verify
    • evidence: forensic-report: 'route_loop._default_commit_stage:420 budget 120s' plan §1: 'route_loop._default_commit_stage:420 budget for git commit 120s'
    • recommendation: No source for the 120s figure is shown except a file:line reference. The measurements establish 2s/302s directly; the 120s is cited as a pre-existing budget. If the 120s is wrong or applies to a different stage, the 'structurally incompatible budgets' claim weakens. This is UNCERTAIN. The design's open question §6.1 correctly flags tightening this budget as optional; the fix does not depend on the 120s being exactly right since post-commit becomes milliseconds. No action required beyond noting the dependency.
  4. [low] Alternative cause not ruled out: post-commit discover could hang for a non-network reason
    • evidence: forensic-report: 'the entire cost is the discover subprocess... which makes real network calls to Gemini and then NVIDIA Build' forensic-report: 'Localizing further: the pre-commit hook via py-run.sh took 1s; the graph refresh with nothing new to do took 5s; an empty commit took 2s.'
    • recommendation: The 302s is attributed to network calls. The 'graph refresh with nothing new to do took 5s' measurement is the key control: it shows the hook machinery itself is cheap. But it does not prove the 302s is network-bound vs., e.g., a cold worktree forcing a full re-discovery of all docs (the forensic report separately notes 'A cold worktree also gives discovery no warm cache, maximizing the work'). The design's §3.5 skip-disposable-tree clause addresses the cold-cache angle, and §3.2 coalescing addresses repeated work — both correct regardless of whether the 302s is network or cache-miss. So this gap does not undermine the fix. Noting it for completeness: the root cause is 'blocking discover in post-commit', and the sub-cause (network vs. cold cache) is not pinned, but the fix does not require pinning it.
  5. [info] Unverified key-rotation hypothesis is correctly quarantined and not load-bearing
    • evidence: forensic-report: 'Unverified hypothesis, kept explicitly as one... NOT measured. It is recorded so a future reader can test it, not rely on it.' plan §8: 'Unverified hypothesis, kept as such... NOT measured.'
    • recommendation: The hypothesis is flagged unverified in both the forensic report and the plan, and the fix's correctness does not depend on it: making post-commit non-blocking resolves the divergence whether discover is slow due to keys, network, or cold cache. The plan's §3.6 visibility (skipped-no-key state) and open question §6.3 (skip when no key) appropriately handle the key-absent path. No change needed; this is the correct treatment of an unverified hypothesis.
  6. [low] Acceptance criterion grq-2 encodes the divergence but may not reproduce the original failure mode
    • evidence: plan §5 grq-2: 'A commit whose post-commit work fails is still reported as SUCCESS by the caller, and HEAD matches what the caller believes.'
    • recommendation: grq-2 asserts the desired invariant but the original failure was a timeout reported as failure, not a post-commit failure. The design should add a criterion: 'a commit whose post-commit work exceeds any caller budget is still reported as SUCCESS and HEAD matches' — i.e., simulate the 120s-budget caller hitting a slow post-commit and confirm no escalation+rollback. grq-1 covers commit-cost independence; grq-2 covers post-commit failure. The timeout-as-failure case sits between them and should be explicit, since it is the exact observed defect.

Lens 2 — does the queue actually fix it

Summary. Queue mechanism review of the graph-refresh async-coalescing design. The core invariant (post-commit must not block, must not influence caller's commit view) is correctly encoded and the split-enqueue/drain-coalesce/lock design is structurally sound. Several concrete interleavings are under-specified: enqueue atomicity on Windows, drain-while-enqueue races, stale-lock recovery safety, unbounded queue growth on persistent discovery failure, and the linked-worktree detection assumption. None are fatal; all are fixable in refinement. Verdict: SOUND-WITH-GAPS.

  1. [high] 1. Enqueue atomicity is unspecified; concurrent commits can corrupt the JSONL queue
    • evidence: §3.1: 'append-only, one JSON object per commit' to .harness/state/graph-refresh-queue.jsonl §3.4: lock is described only for the drainer, not for enqueue writers Forensic context: Windows host (C:\tmp path in collateral), where atomic append semantics differ from POSIX
    • recommendation: Specify the enqueue write primitive explicitly. On POSIX, O_APPEND + a single write() of a serialized line is atomic for small payloads; on Windows it is not guaranteed. Either (a) use the SAME lock for enqueue (cheap fcntl/LockFileEx, held for microseconds) or (b) write each entry to a per-commit temp file and atomically rename into a spool dir the drainer globs. The design must state which and grq-4 must cover two concurrent enqueues, not just two concurrent drainers.
  2. [high] 2. Drain-while-enqueue race is not addressed; the drainer can miss entries it should have coalesced
    • evidence: §3.2: 'drainer reads ALL pending entries, unions their paths' — implies a snapshot §3.4: lock is held by the drainer but §3.1 enqueue is described as lock-free append No statement of whether enqueue is blocked/buffered while the drainer holds the lock
    • recommendation: Define the drain protocol as: drainer acquires lock → snapshots current queue → truncates/rotates the queue file (or moves it aside) → releases lock → runs discovery on the union. Entries enqueued after the snapshot stay for the NEXT drain. This is safe but means a commit landing during a long discovery waits for the next drain — acceptable, but must be stated. Alternatively, enqueue blocks on the lock (milliseconds) so the drainer sees a consistent set. Pick one and encode it in grq-3/grq-4. The current text leaves a gap where a commit enqueues between snapshot and truncation and is then truncated.
  3. [medium] 3. Stale-lock recovery can double-run discovery if the killed drainer was not actually dead
    • evidence: §3.4: 'a hard-killed drainer must not wedge the queue forever' + 'stale-lock age' No description of how staleness is measured (mtime? PID liveness?) or what happens if the lock is reclaimed while the old process is still alive
    • recommendation: Stale-lock recovery must be safe against the 'not actually dead' case. Use lock-content with PID + starttime, and verify the PID is gone (not just that the lock is old) before reclaiming. If only mtime is used, a slow-but-alive drainer (e.g., paged out, or a long Gemini retry) can have its lock stolen mid-run, producing two concurrent discoverers — the exact corruption §3.4 claims the lock prevents. grq-4 should assert the stale-lock path only fires when the owning PID is confirmed dead.
  4. [medium] 4. Unbounded queue growth when discovery persistently fails is not bounded
    • evidence: §3.6: 'a queue that never drains becomes a WARN' — visibility only, no compaction §6.3: open question on whether unattended API calls should be capped/skipped — unresolved No max-queue-depth or max-entry-age in acceptance criteria
    • recommendation: Add a compaction rule: the drainer coalesces ALL pending entries into one drain regardless of count, so a failed drain does not cause N retries for N entries — it causes one retry per drain trigger. Additionally cap queue depth (e.g., drop/merge entries older than X with a WARN) so a long-unattended repo does not accumulate months of JSONL. grq-6 should assert depth stays bounded after repeated failed drains, not just that the WARN fires.
  5. [medium] 5. Coalescing by union-of-paths is correct for the stated use but the design does not justify why per-commit granularity is unneeded
    • evidence: §3.2: 'unions their paths, dedupes, and runs ONE discovery pass' No statement of whether discovery output is path-keyed or whole-graph If graphify-out/ is a whole-graph artifact, union is obviously correct; if it is per-path, coalescing could drop per-path provenance
    • recommendation: State explicitly that discovery produces a whole-graph artifact (or that per-path results are independent and idempotent under re-run). If discovery is idempotent and whole-graph, union-of-paths is strictly correct and loses nothing. If there is any per-commit provenance (e.g., 'this edge came from commit X'), coalescing loses it — but the forensic report gives no evidence of such provenance, so this is likely fine. Mark UNCERTAIN pending confirmation that graphify-out/ is not per-commit-keyed. Add one line to §3.2.
  6. [medium] 6. Linked-worktree detection via git-common-dir vs git-dir is correct in principle but fragile on edge cases
    • evidence: §3.5: 'detectable via git rev-parse --git-common-dir differing from --git-dir' This is the standard test for a linked worktree and is the right primitive UNCERTAIN: behavior inside a 'git worktree add' that shares a common dir but where the hook runs with a different GIT_DIR env — the test should still hold but is not asserted against the actual hook environment
    • recommendation: The detection primitive is sound. Add to grq-5 an assertion run inside a real 'git worktree add' tree (not mocked), confirming the hook sees the divergence and skips. Also handle the bare-repo case (no worktree) where both resolve identically — that is the 'not a worktree' case and enqueue should proceed normally. The design text should distinguish 'I am the main worktree' (enqueue) from 'I am a linked worktree' (skip).
  7. [low] 7. Append-only JSONL is the right shape but the 'root' field creates a multi-root ambiguity the drainer must resolve
    • evidence: §3.1: entry shape {sha, paths, at, root} §3.5: skip from linked worktrees — but if ANY entry leaks through from a worktree, its 'root' differs from the main root Drainer is described as running discovery with cwd=root; which root?
    • recommendation: Either drop 'root' from the entry (drainer always uses the main repo root, and paths are repo-relative) or specify that the drainer groups entries by root and refuses/ warns on foreign roots. Repo-relative paths are the safer choice because they survive a repo move and make union/dedupe trivial. The current shape invites a bug where a worktree entry with an absolute 'root' is drained against the wrong tree. Recommend: store repo-relative paths only; drainer resolves cwd itself.
  8. [low] 8. grq-1's '~2s ceiling with network unreachable' does not pin the invariant that matters
    • evidence: §5 grq-1: 'post-commit's own wall time stays under a small ceiling (~2s) with the network unreachable' The original bug was network REACHABLE taking 302s; testing with network unreachable proves the no-network fast path but not that a reachable network cannot re-block
    • recommendation: Add to grq-1: 'and post-commit wall time stays under the same ceiling with the network REACHABLE but the drainer detached' — i.e., prove enqueue does not wait on discovery even when discovery would succeed. The network-unreachable variant is necessary but not sufficient; it tests the skip path, not the detach path. Both variants needed.
  9. [low] 9. The 'both' drain trigger (§6.2) doubles the surface for the same lock; the design leans 'both' without justifying the cost
    • evidence: §6.2: 'I lean both, minimally' — belt and braces §3.4: the lock is 'load-bearing, not hygiene' — so two trigger paths both contending on a load-bearing lock is more failure surface, not less
    • recommendation: Prefer the detached one-shot as the primary trigger (it runs promptly after commit) and the opportunistic check as a fallback for when the detached drainer was killed or skipped (e.g., no key). 'Both' is fine only if the lock protocol is proven in grq-4 against all three races (enqueue/drain, drain/drain, stale/drain). The design should not lean 'both' until that proof exists; default to detached-primary + opportunistic-fallback.
  10. [info] 10. The 120s route_loop budget (§6.1) is correctly deferred but the relation assertion should be a hard acceptance criterion, not an open question
  • evidence: §6.1: 'I lean yes — assert the relation (any post-commit ceiling < any caller's commit budget) in a test' Forensic report: 'Both numbers were chosen independently; nothing asserts a relation between them' — this is the structural defect, not just a tuning issue
  • recommendation: Promote the relation assertion from open question to acceptance criterion: add grq-8 'post-commit wall ceiling < route_loop commit budget, asserted in a test that fails the build if violated'. The forensic report explicitly identifies the missing relation as the structural cause; leaving it as a lean keeps the same class of bug alive. This is the single most important change.

Lens 3 — skip clauses & environment detection

Summary. Skip-clause review of the graph-refresh queue plan. The two skip conditions (linked worktree, active gate hold) are real and necessary but incomplete and racy. Five concrete gaps: (1) linked-worktree detection wrongly suppresses developers who use worktrees for normal work — the plan conflates 'disposable gate shard' with 'any linked worktree'; (2) TOCTOU between the hold check and the append silently drops entries; (3) the skip set is open-ended — CI, submodules, bare clones, and non-gate automation are unhandled; (4) detection primitives are asserted but not specified, and --git-common-dir vs --git-dir is unreliable on Windows and on bare repos; (5) the plan never defines what the drainer does with an entry whose root no longer exists, which the worktree skip exists to prevent but cannot fully guarantee. Verdict: SOUND-WITH-GAPS; the single most important change is to stop keying the worktree skip on 'linked worktree' and instead key it on an explicit marker the gate writes int

  1. [high] Linked-worktree skip wrongly suppresses legitimate worktree-based development
    • evidence: §3.5: 'detectable via git rev-parse --git-common-dir differing from --git-dir, i.e. I am a linked worktree' §3.5 rationale: 'the tree is deleted right after; the entry would name paths that no longer exist' Forensic report: 'each shard is a disposable detached worktree pinned to HEAD' — the disposability is the real signal, not linkedness
    • recommendation: Do not key the skip on linked-worktree status. Key it on an explicit marker the gate writes into the shard (e.g. .harness/state/disposable-shard or an env var the gate sets when spawning the worktree). A developer using git worktree add for normal parallel work must still get their graph refreshed. The plan's own §3.5 says the problem is 'the tree is deleted right after' — so detect deletion-intent, not linkedness.
  2. [high] TOCTOU: a gate hold starting between the hold-check and the append silently drops the entry
    • evidence: §3.5: 'a gate hold is active (.harness/runs/gate-hold/ non-empty) — writes to .harness/ during a hold are discarded' §3.5: the check and the append are described as separate steps with no atomicity guarantee
    • recommendation: The hold check and the append must be atomic with respect to hold acquisition, or the entry must be written to a location the hold does not swap. If the hold swaps .harness/state/ on acquisition, an entry appended microseconds before the swap is lost with no signal. Either (a) write the queue outside the swapped subtree, (b) have the hold-acquisition path itself drain or snapshot the queue, or (c) accept the loss but make §3.6's doctor check detect 'entry count went backwards' as a WARN. The plan currently treats the hold clause as sufficient when it is racy.
  3. [medium] Skip set is incomplete — CI, submodules, bare clones, and non-gate automation are unhandled
    • evidence: §3.5 lists only two skip conditions; §6 open questions does not raise CI or submodules Forensic report collateral: 'a probe that can hang spinning' — the plan does not address other automated committers
    • recommendation: Enumerate the full committer taxonomy and decide for each: human (enqueue), gate shard (skip via marker), CI (skip or enqueue to a CI-local queue?), bare-clone operations (no post-commit hook fires — is that intended?), submodules (the hook runs per-repo; a submodule commit during a superproject operation should enqueue against the submodule root, which may be a linked worktree — see finding 1). The plan should state the default for 'unknown committer' explicitly rather than implicitly enqueueing.
  4. [medium] Detection primitives are asserted but not specified; --git-common-dir vs --git-dir is unreliable on Windows and bare repos
    • evidence: §3.5: 'detectable via git rev-parse --git-common-dir differing from --git-dir' §5 grq-5: 'asserted on real git state, not mocked' — but the git state itself is platform-dependent
    • recommendation: Specify the exact detection command and its behavior on: Windows (path casing, junctions), bare clones (common-dir == git-dir, but there is no working tree), submodules, and older git versions where --git-common-dir semantics differ. UNCERTAIN whether --git-common-dir is stable across the git versions the project targets. The acceptance criterion grq-5 should include a Windows-linked-worktree case or explicitly document the platform scope.
  5. [medium] No handling defined for an enqueued entry whose root vanishes before drain
    • evidence: §3.2: drainer 'reads ALL pending entries, unions their paths, dedupes' §3.5: worktree skip exists because 'the entry would name paths that no longer exist' — but the skip is a precondition, not a guarantee, and finding 2's TOCTOU can defeat it
    • recommendation: The drainer must validate each entry's root exists and its sha is still reachable before spending API calls. If root is gone or sha is not in the repo, drop the entry and record skipped-stale-root in the drain outcome (surfaced via §3.6). This is the defense-in-depth that makes the worktree skip non-load-bearing; today the plan treats the skip as the guarantee, which it cannot be under TOCTOU.
  6. [low] grq-5 acceptance is asserted on 'real git state' but does not cover the negative space — legitimate worktree user
    • evidence: §5 grq-5: 'No enqueue from a linked worktree; no enqueue while a gate hold is active. Both asserted on real git state, not mocked.'
    • recommendation: Add a grq-5b: a commit in a linked worktree WITHOUT the disposable-shard marker DOES enqueue and the graph IS refreshed. Without this, finding 1's regression is untested and the plan can ship while silently breaking worktree users.

Lens 4 — failure visibility of going async

Summary. The async-visibility answer is insufficient: doctor WARN is pull-based and opt-in, so an operator who never runs doctor sees nothing. The design has no push-path alarm, no failure-mode distinction, no quota guard, and no staleness propagation to graph consumers. See findings 1-5.

  1. [high] doctor WARN is pull-based; an operator who never runs doctor sees no signal at all
    • evidence: §3.6: 'Add to the existing graph-status verb and the doctor check set' — both are operator-invoked §5 grq-6: visibility is asserted only as 'surfaces as a doctor WARN' No mention of any push-path (commit-time message, non-zero exit on next harness command, or log file the operator already reads)
    • recommendation: Add a push-path signal that does not require the operator to opt in. Concretely: (a) post-commit prints a one-line '[graph-refresh] queued N paths (drain pending)' to stderr on commit — visible at the exact moment the operator is watching git output; (b) the next harness command that finds a non-empty queue older than threshold prints a WARN to its normal output stream and exits non-zero ONLY in a dedicated 'harness health' sense, not on arbitrary commands. The doctor check is a backstop, not the primary channel.
  2. [high] A drainer that always fails for the same reason produces a WARN that looks identical to 'slow but fine' — no failure-mode distinction
    • evidence: §3.6: last drain's outcome is 'ok | failed | skipped-no-key' — three buckets §5 grq-6: asserts only depth + age, not a distinct alarm for repeated-identical failure No counter for consecutive failures or a 'last-failure-reason' that escalates after N repeats
    • recommendation: Track consecutive-failure count and last-failure-reason in the queue state. After K consecutive identical failures (e.g. 3), escalate from WARN to a louder signal — and, critically, record the reason string (auth, network, quota, parse) so the operator can tell 'broken setup' from 'transient'. grq-6 should assert that N consecutive failures with the same reason produce a distinct, named alarm, not just 'queue depth > 0'.
  3. [high] Unattended discovery burns API quota with nobody watching; no per-drain cap and no circuit breaker
    • evidence: §6 Q3: 'Should the drainer be allowed to spend API calls unattended at all?' left as an open question §3.3: detached one-shot drainer is fire-and-forget, 'never awaited' forensic report: discover 'makes real network calls to Gemini and then NVIDIA Build'
    • recommendation: Resolve Q3 now, not defer it. Require: (a) a per-drain path-count cap (e.g. drain at most M paths per invocation, leave the rest queued) so a backlog cannot spend unbounded quota in one shot; (b) a circuit breaker — if the last drain failed with auth/quota/network reason, do NOT immediately retry on the next trigger; back off. Leaving this open in a plan that explicitly removes the human-present check is the gap.
  4. [high] A stale graph can make some OTHER harness decision wrong, and nothing propagates the staleness to graph consumers
    • evidence: §3.6 acknowledges 'the graph is briefly stale by design' but only surfaces staleness via doctor/queue-depth No mechanism described whereby a consumer of graphify-out/ checks a freshness marker before trusting it forensic report frames the original bug as 'Git's truth and the orchestrator's belief diverged' — the async design risks the same shape: graph truth vs. graph-consumer belief
    • recommendation: Write a freshness marker alongside graphify-out/ (e.g. last-successful-drain sha + timestamp). Any harness subsystem that reads the graph MUST check the marker against current HEAD and, if stale beyond a threshold, either refuse with a named 'graph-stale' outcome or degrade explicitly — never silently use a stale graph as if it were current. This is the consumer-side counterpart to §3.6 and it is absent.
  5. [medium] 'skipped-no-key' is the right outcome ONLY if it is loud; as specified it is a quiet bucket that hides a broken setup
    • evidence: §3.6: 'skipped-no-key' is one of three last-drain outcomes, surfaced only via doctor §6 Q3 floats 'Skip when no key (report skipped-no-key rather than failing)' No assertion that skipped-no-key is an ERROR-class signal vs a WARN, nor that it blocks graph-dependent operations
    • recommendation: Pick: skipped-no-key is a WARN if a key is genuinely optional for the operator's workflow, but an ERROR if any graph consumer is about to run. The design must state which, and grq-6 must assert that a drain that exits skipped-no-key does NOT clear the WARN — only 'ok' clears it. As written, 'skipped-no-key' could be recorded as a non-failure and silently clear the alarm, hiding a broken key setup.
  6. [medium] grq-6 asserts the happy clearing path but not the failure-escalation path; the acceptance criterion is asymmetric
    • evidence: §5 grq-6: 'a successful drain clears it' — only the clear path is named No criterion asserting that a persistently-failing drain does NOT clear the WARN, nor that repeated failure escalates
    • recommendation: Split grq-6 into grq-6a (undrained queue older than threshold → WARN naming depth) and grq-6b (N consecutive identical drain failures → distinct alarm that is NOT cleared by a subsequent skipped-no-key or failed drain, only by an 'ok'). The acceptance must cover the failure loop, not just the clear.
  7. [low] UNCERTAIN: no log file specified for the detached drainer's own output — if it fails, the failure reason may be unrecoverable
    • evidence: §3.3: drainer is 'fire-and-forget, never awaited' §3.6 records 'last drain's outcome' but not where the drainer writes its detailed stderr/stdout No mention of a drainer log path under .harness/state/
    • recommendation: Specify a drainer log (e.g. .harness/state/graph-refresh-drain.log, rotated) that captures the discover subprocess's stderr verbatim. The 'last drain outcome' in §3.6 is a summary; the detailed reason must be retrievable without re-running. This is also the evidence a future forensic report would need.
