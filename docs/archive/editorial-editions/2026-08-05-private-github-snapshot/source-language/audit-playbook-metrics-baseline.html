2. Owner-metric mapping

(a) tokens per delegation -- ANSWERED by cost-metrics.json delegation.estTokens (a chars/4 estimate per the module's own doc-comment; observedTokens exists as a field on chat-turn rows and capsule_cost() output but is not populated on delegation rows) aggregated via byModel/byModelCTS. Caveat: the store is a 500-row ring; at 251 delegation rows already consuming half the ring, effective delegation-only history shrinks as gate/chat-turn/workflow rows compete for the same 500 slots.

(b) defects in delegated work -- PARTIALLY ANSWERED. outcome (kept/partial/rejected/reworked) on delegation rows is the closest existing defect signal; _cts()/track_record already compute usefulRate = (kept+reworked)/judged. GAP: review --plan WARN rows and oracle-mutate survival counts -- the two other candidates the owner's framing named -- are NOT persisted anywhere found (print-only, no jsonl/state sink); reckon verdicts are consumed by gate-policy code but no dedicated verdict-history store was located. "Defects" today = the coarse 4-way outcome label only.

(c) delegation outcome rates over time -- PARTIALLY sufficient for a BEFORE baseline: 251 delegation rows spanning 2026-07-13..2026-07-30 (17 days), outcome distribution kept=215, rejected=24, reworked=8, partial=3, 1 null -- real signal, and track_record's own MIN_N=8 threshold already treats this as enough to escape "insufficient-data" for the dominant model+agentType groups. GAP: the 500-row hard ring cap means "over time" trending will silently truncate -- gate rows alone are 150 of the 500 slots as of this snapshot covering only 2 days, and chat-turn's window already stops 2026-07-23 (7 days stale), evidence that eviction of older delegation history is happening NOW.

(d) injected prompt bytes per role per session -- GAP, confirmed single-datapoint. No store found (cost-metrics.json has no byte/prompt-injection field; search-telemetry.jsonl tracks search calls, not injection payloads) beyond the one static 2026-07-15 comment in context_diet.py and the 2026-07-29 audit snapshot referenced by the intake doc (audit-playbook-injection-surfaces.md, not independently re-verified in this pass). This is the one metric with zero time-series history -- a snapshot audit, not a meter.

3. Verdict

Historical record is sufficient as a phase-0 BEFORE-baseline for (a) tokens/delegation and (c) outcome-rate trends, with a caveat: the 500-row ring on cost-metrics.json is actively evicting older rows (chat-turn already 7 days stale) and will keep shrinking the usable window as gate-record volume grows -- any BEFORE snapshot for the compiler comparison should be exported/frozen from the ring NOW, not re-derived later from a post-compiler state of the same file.

It is NOT sufficient for (b) defects beyond the coarse kept/partial/rejected/reworked label -- review-WARN and mutate-survival signals exist as code but not as persisted series, so any defect-rate claim finer than the 4-way outcome bucket needs a new sink added where overseer_review.py and the mutate-oracle already compute their verdicts in memory (cheap -- the computation exists, only persistence is missing).

It is NOT sufficient for (d) injected bytes/session -- genuinely absent as a time series; the intake's own phase-0 scope item (injected bytes/tokens per role per session, recorded before compiler code) is correctly scoped, since today it is one manual audit snapshot, not an ongoing measurement.

Minimal dedicated meter for AFTER-vs-baseline (matches the intake's own ask): (1) append to whatever hook injects role prompts today, logging ts/role/session/bytesInjected/sourceCount to a new jsonl (mirrors the search-telemetry.jsonl pattern already in this repo) -- closes gap (d); (2) one append_event/write_json call each where overseer_review.py assembles WARN rows and where the mutate-oracle finalizes survivors -- closes gap (b); (3) no new work needed for (a)/(c) -- export the current cost-metrics.json delegation slice as the frozen BEFORE snapshot given the ring is live-evicting.
