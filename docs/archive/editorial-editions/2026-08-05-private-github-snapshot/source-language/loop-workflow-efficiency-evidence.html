Front 1 — Kill re-gate churn / incremental validation (→ Brief A)

[web] Bazel's remote cache stores action outputs (build and test actions) in a content-addressable store keyed by a SHA-256 digest of the action's inputs; an action-cache hit skips re-execution entirely and just fetches the prior output. Remote Caching — Bazel docs current WebSearch returned direct quotes from the official docs page (not separately WebFetched). Caching correctness assumes hermetic, deterministic actions; the cache itself does not decide which tests are "affected" by a change — that's a separate query/analysis step (see bazel-diff below). forte producao
[web] Google's TAP (Test Automation Platform) computes "AFFECTED" test targets as the reverse-dependency closure over a changelist's changed files, using the build dependency graph; a 2016-era internal study covered >500K changelists, 5.5M unique test targets, 4B+ test outcomes. Memon & Gao, "Taming Google-Scale Continuous Testing" (Google Research / ICSE-SEIP 2017) — https://research.google.com/pubs/archive/45861.pdf paper 2017 Two WebFetch attempts on the PDF (direct and via its 302 redirect) both returned undecodable/garbled binary text — the affected-targets mechanism and the scale numbers come from the search engine's snippet of the paper, not from my own read. [web] Ekstazi (dynamic-dependency regression test selection, Java/Scala): tracks each test's runtime file dependencies via classfile checksums, needs no VCS integration, and is evaluated at file/class granularity (found to beat method-level granularity). Companion measurement: reduces end-to-end test time 32% on average, 54% for longer-running suites, across 615 revisions of 32 OSS projects. Gligoric, Eloussi, Marinov — "Practical Regression Test Selection with Dynamic File Dependencies" (ISSTA 2015) + tool paper "Ekstazi: Lightweight Test Selection" (ICSE 2015 demo) — https://users.ece.utexas.edu/~gligoric/papers/GligoricETAL15EkstaziTool.pdf , https://github.com/gliga/ekstazi paper + repo 2015 WebFetch on the tool-paper PDF partially decoded (mechanism + false-positive/negative tradeoff confirmed directly); the 32%/54% figure came from the WebSearch snippet of the companion measurement paper, not my own fetch of that PDF. Design explicitly favors safety (over-selection / false positives that waste cycles) over precision; no soundness guarantee documented for reflection/dynamic classloading edge cases. moderada prototipo/validado (research tool with reported industry adoption; not vendor-backed)
[web] pytest-testmon selects affected tests by tracing test↔code dependencies with coverage.py (line-level), diffing against a stored DB; it explicitly does not track static data files or external network services, and intentionally over-selects on signature-shape changes (a parameter rename invalidates the whole parameter→method→class→module hierarchy) as a documented safety-over-precision tradeoff. testmon.org (official docs) + https://github.com/tarpas/pytest-testmon docs + repo current Direct WebFetch of testmon.org; quotes captured from decoded page text. coverage.py-based tracing has known blind spots (dynamic imports/monkeypatching); env-var/package-version tracking is partial. forte producao (widely-used pytest plugin, community-maintained not vendor-backed)
[web] Nx computes a per-task hash from source files + relevant config + dependency versions + user-provided runtime values + CLI flags; on a hash match it replays the cached artifact + terminal output instead of re-running, checking local cache first then remote. Documented gotcha: only script-level args count toward the hash, not wrapper-CLI flags (nx build x vs nx run-many -t build -p x hash identically even though only one passed via the wrapper). How Caching Works — Nx (official docs) docs current Direct WebFetch, quotes captured from decoded page text. The wrapper-CLI-flag gotcha is a real silent-staleness risk if hash "inputs" aren't configured carefully — directly relevant if we ever key a cache on a partial fingerprint. forte producao
[web] Turborepo maintains a local+remote content-addressable cache; task inputs are hashed into a "fingerprint," and a fingerprint match causes turbo to download/replay the cached artifact and logs instead of re-executing, with HMAC-SHA256 signing for integrity on the remote cache. Remote Caching — Turborepo (official docs) docs current WebFetch of the remote-caching page itself stated it does not contain the hash-computation mechanics (defers to a separate "caching fundamentals" page I did not fetch); the "fingerprint = hash of inputs" description rests on the WebSearch synthesis, not my own read of primary text for that specific claim. [web] bazel-diff / target-determinator (third-party, not Bazel-core): compute the exact affected-target set between two git revisions by diffing the Bazel query graph — "directly impacted" (changed rule attrs / source deps) vs "indirectly impacted" (transitive dependents); README claims usage at "tens of thousands of targets" scale. Tinder/bazel-diff (README) repo ongoing (v4.0.8+ seen) WebSearch snippet quoting the README directly; not separately WebFetched. [web] Anthropic's multi-agent research system: a lead-researcher orchestrator spins up 3-5 subagents in parallel (not serially), and each subagent itself parallelizes 3+ tool calls; internally measured ~90% research-time reduction on complex queries and a 90.2% win-rate vs single-agent Claude Opus 4 on their internal eval — at a token-cost multiplier of ~15x a single chat turn (a lone agent already runs ~4x a chat turn). Documented limitation: subagents currently execute synchronously under the lead agent (no cross-subagent real-time steering/coordination), the system is non-deterministic run-to-run even with identical prompts, and small orchestrator-prompt edits can unpredictably change subagent behavior. Anthropic Engineering — How we built our multi-agent research system blog (vendor engineering post) 2025 Direct WebFetch of the primary URL; quotes captured from decoded page text. Self-reported vendor case study of Anthropic's own shipped product — no independent replication of the 90%/90.2%/15x figures; they are specific to Anthropic's internal research eval, not a general law. moderada producao (shipped product feature)
[web] LLMCompiler: an explicit Planner → Task-Fetching-Unit → Executor architecture that identifies which LLM function-calls are independent vs interdependent and issues the independent ones concurrently; reports up to 3.7x latency speedup, up to 6.7x cost reduction, ~9% accuracy improvement vs sequential ReAct-style calling across benchmarks. Kim et al., "An LLM Compiler for Parallel Function Calling," ICML 2024 — https://arxiv.org/abs/2312.04511 , https://github.com/SqueezeAILab/LLMCompiler paper 2024 (arXiv Dec 2023; ICML 2024) WebSearch snippet quoting the abstract/results; not separately WebFetched in full. [web] "Speculative Actions": a lightweight draft model speculatively pre-executes candidate next-actions while the main LLM is still reasoning; when the main model decides, a matching speculated action's precomputed result is reused (cache-hit), a mismatch discards the speculative work and runs the true action — provably lossless (identical final behavior to fully sequential execution). Reports ~1.5-2.5x end-to-end latency reduction, more when action-execution time dominates reasoning time. Authors flag: effectiveness depends on draft-model prediction accuracy, and coordinating multiple execution streams adds system complexity. Ye et al., "Speculative Actions: A Lossless Framework for Faster Agentic Systems" — https://arxiv.org/abs/2510.04371 paper (preprint) 2025 (arXiv Oct 2025) Direct WebFetch of the PDF; summary extracted from decoded text. Single preprint, not yet cross-validated by other groups; peer-review/venue status unclear from what I could access. This is exactly the risk shape of "gate the tree speculatively while review/reckon proceed" (Brief B) — same lossless-if-verified structure, same "coordination adds complexity" caveat. preliminar prototipo
[web] GNU Make -j/--jobs: computes the full prerequisite DAG before running any recipe, then executes independent targets concurrently up to N jobs; .NOTPARALLEL and .WAIT are explicit escape hatches to force serial ordering where a real hazard exists. GNU Make Manual — Parallel (the tool's own reference manual) docs current (evergreen manual) WebSearch synthesis quoting the manual directly; not separately WebFetched. Correctness of -j depends entirely on the Makefile's dependency graph being complete and accurate — an under-specified graph causes silent races. Mirrors our own INTERDEPENDENT class needing explicit sync barriers, not just an "assume it's fine" flag. forte producao (30+ year old, ubiquitous)
[web] Apache Airflow: DAGs declare task dependencies explicitly (>>/<< or set_upstream/downstream); the default trigger rule is "run only when ALL upstream tasks succeeded," but trigger_rule (all_success/one_success/etc.) can express OR-style joins; the scheduler resolves dependencies at DAG-serialization time. Airflow docs — Dags, Tasks docs current WebSearch synthesis quoting official docs directly. Docs-only, not independently benchmarked; Airflow's scheduling unit is a whole DAG run, coarser-grained than a per-subagent-step target — the concept (explicit dependency declaration + configurable join semantics) transfers better than the tool itself would. forte producao
[web] Dagster's software-defined assets form a DAG inferred from declared data dependencies (no manually-maintained DAG object); the default multiprocess executor runs each step in its own process and independent steps run in parallel automatically; tag_concurrency_limits throttles how many ops with a given tag can run concurrently. Dagster docs — assets, execution docs current WebSearch synthesis quoting docs; not separately WebFetched. Front 4 — Agile / lean frameworks, foundations (→ Brief B + C, theoretical grounding)

claim source (URL/citation) type year method limitations confidence class maturity
[web] Theory of Constraints: a system's throughput is bounded by its single (or few) constraint(s) ("the drum"). Drum-Buffer-Rope schedules the constraint at its own sustainable pace, protects it with a time buffer, and paces upstream release via a "rope" tied to the constraint's actual consumption rate — releasing work faster than the constraint can process only builds inventory/WIP, not throughput. Goldratt & Cox, The Goal (1984, North River Press) — mechanic corroborated across Theory of Constraints — Wikipedia, TOC Institute, Lean Production — TOC, Scholarpedia — Theory of Constraints book (management monograph, not peer-reviewed academic paper) 1984 WebSearch synthesis across multiple independent secondary explainer sites cross-referencing each other; did not directly fetch/read Goldratt's own books. The exact book where the term "Drum-Buffer-Rope" itself first appears is disputed between my own sources — one (AllAboutLean) attributes the name to the later book The Race (Goldratt & Fox, 1986), while others associate the detailed DBR scheduling mechanics with The Haystack Syndrome (1990). I could not resolve this bibliographic discrepancy this round — flagging explicitly rather than picking one. The underlying mechanic (constraint paces the whole system) is consistent across every source. moderada validado (decades of case studies, widely adopted)
[web] Critical Path Method: Kelley (Remington Rand) & Walker (DuPont) developed project-scheduling algorithms at DuPont from 1956, published "Critical-Path Planning and Scheduling" at the Dec 1959 Eastern Joint Computer Conference; DuPont's application reportedly saved ~25% on plant shutdown/restart schedules by identifying which tasks actually gate the end date (the critical path, zero slack) vs which have slack — i.e., don't uniformly add labor, focus effort on the tasks that are actually on the critical path. Kelley & Walker, "Critical-Path Planning and Scheduling" (1959 EJCC proceedings); retrospective account: PMI — Origins of CPM, a Personal History (Kelley's own first-person account) paper (conference proceedings) + first-person historical account 1959 WebSearch synthesis; the PMI link is Kelley's own retrospective, close to primary but not separately WebFetched this round. The "~25% savings" figure comes from a secondary summary (Bizfluent), not re-verified against the 1959 proceedings text directly. moderada validado (canonical PM technique, used everywhere)
[web] Kanban WIP limits: David J. Anderson's own stated definition — "if there is no explicit limit to work-in-progress and no signaling to pull new work through the system, it is not a kanban system" — makes an explicit WIP cap + a pull signal the defining property, not an optional add-on. Traces to Taiichi Ohno's kanban cards at Toyota (1940s-50s), itself adapted from US supermarket restocking practice. David J. Anderson, Kanban: Successful Evolutionary Change for Your Technology Business (2010, Blue Hole Press) — definition corroborated via djaa.com — Revisiting the Principles and General Practices of the Kanban Method (Anderson's own consultancy site); Toyota origin via Ohno (see next row). book 2010 (software adaptation) / 1940s-50s (Toyota origin) WebSearch synthesis; the quoted definition is from Anderson's own site (as close to primary as available without the physical book). Did not fetch/read the 2010 book itself (no stable URL). forte producao — maps directly onto Brief C's "WIP limit = 1 in the COMMIT stage but >1 upstream"
[web] Lean one-piece-flow: Taiichi Ohno describes continuous single-unit flow as the ideal state of production (vs batch-and-queue), while explicitly noting in his own writing that pure one-piece-flow is "extremely difficult and... not always even practical." Taiichi Ohno, Toyota Production System: Beyond Large-Scale Production (1978 Japanese orig., 1988 English trans., Productivity Press) — paraphrase corroborated via secondary sources (ineak.com, leansmarts.com) book 1978/1988 WebSearch synthesis of secondary paraphrase of Ohno's own book; did not fetch the book directly. Secondary-source paraphrase, not my own read of Ohno's text — but the substance (one-piece-flow is the ideal; batching is an acknowledged compromise) is consistent across every source found. moderada validado
[web] Little's Law (L = λW): the long-run average number of items in a system equals the average arrival rate times the average time each item spends in the system; holds for any stable, stationary, work-conserving queueing system regardless of the arrival/service distribution. Proven by John D.C. Little, "A Proof for the Queuing Formula: L = λW," Operations Research 9(3):383-387 (1961), DOI 10.1287/opre.9.3.383. Direct application to our loop: WIP = arrival-rate × cycle-time — cutting cycle-time (this round's whole goal) directly cuts WIP for the same throughput; conversely, admitting more WIP without cutting per-item wait just inflates cycle time. J.D.C. Little, Operations Research 9(3), 1961 — citation corroborated across Wikipedia — Little's law and the MIT-affiliated retrospective "Little's Law as Viewed on Its 50th Anniversary" paper 1961 WebSearch synthesis with well-corroborated citation metadata (journal, volume, pages, DOI) across independent sources; did not fetch the 1961 paper itself (likely paywalled). Did not read full original text — treated as reliable given cross-corroboration and its status as an undisputed, widely-cited foundational result. forte validado (foundational, undisputed queueing-theory result)
[judgment] Applying Little's Law to the round's own numbers: if a demand's end-to-end cycle time (W) went from ~15-30min to 20min-1h+ while arrival rate (λ, how often we start a new demand) hasn't dropped, WIP inside the pipeline (L) rose proportionally — meaning the re-gate churn diagnosis (Brief A) isn't just "slower," it's "more concurrent half-finished work sitting in the system," which is exactly the pressure that motivates Brief C's cross-item pipelining (spend the now-larger L productively instead of idling it). — (my own reasoning applying the Front-4 Little's-Law row to the round doc's §1b numbers) n/a n/a n/a This is an inference from a proven law applied to informally-observed numbers (the round doc's own [judgment]-tagged durations), not a new measurement. teorica conceitual

[web] Ford's moving assembly line (Highland Park; first flywheel-magneto line early 1913, full chassis line Oct 7 1913): splitting one worker's whole-unit assembly into ~29-140 fixed stations along a moving line cut per-unit build time from ~12hr 8min to ~1hr 33min. Real-world model for cross-item pipelining: unit N+1 enters station 1 while unit N is at station 5 — exactly Brief C's "item N+1 in PLANNED/IMPLEMENTING while item N is in GATING." [web] Mise en place ("everything in its place"): professional kitchens front-load all prep (chopping, portioning, sauce bases) before service starts, so the timed, customer-facing cook-and-plate step is short and uninterrupted; commonly attributed to Auguste Escoffier's late-19th-century kitchen brigade system. Maps to Brief D: pre-derive shared context (the ~12k tok required-reads) before the timed critical-path work starts, rather than cold-spawning context-derivation on the clock. Multiple independent culinary-education sources converging on the same attribution: Escoffier School, Michelin Guide, Culinary Arts Switzerland docs (educational/institutional, not academic) attribution ~1890s; pages current WebSearch synthesis, cross-corroborated across independent culinary-education sources — no single peer-reviewed primary source exists for a practice this old. This is a practice, not a measured performance claim — confidence here is about the historical attribution being consistent, not about any number. moderada n/a

Releasing work into COMMIT faster than the gate can drain it doesn't speed up the system; it just grows the WIP queue sitting in front of the gate. — (my own analogical construction; I did not find, and did not go looking for, a specific paper that frames ramp metering explicitly as "DBR for traffic") n/a n/a n/a Explicitly not a web-verified claim — register as judgment, not evidence. opiniao conceitual

TOP LEADS FOR OUR PROBLEM

Ranked by how directly each attacks the two confirmed bottlenecks (re-gate churn, gate-as-constraint), tied to the round's own briefs:

  1. Fingerprint-keyed gate-result cache (Nx / Turborepo / Bazel remote-cache pattern) → Brief A. This is the highest-leverage lead because it's the smallest delta from what we already have: SPEC-157 already computes a staged fingerprint. Nx/Turborepo/Bazel all implement exactly "hash inputs → on match, skip execution and replay the cached PASS" at production scale. We don't need to invent the mechanism, only wire our existing fingerprint into a cache-or-run decision before paying for a full 7-15 min re-gate on a tree that (partially) already passed. Confidence moderada→forte depending on which vendor's docs you weight; maturity producao across all three.

  2. Affected-target/test selection (Google TAP's reverse-dependency closure, bazel-diff, Ekstazi, pytest-testmon) → Brief A's other half. Where the fingerprint cache answers "did this exact tree already pass," affected- target selection answers "which subset of the scenario+spec-pack surface does this diff actually touch." This is genuinely new work for us (we'd need a changed-paths → scenarios dependency map we don't have today), but every one of these four tools proves the pattern works at scale (Google: billions of test outcomes; Ekstazi: 32-54% time reduction measured across 32 OSS projects). Pair with lead #1: fingerprint cache kills identical re-runs, affected-selection kills unnecessary re-runs on genuinely new diffs.

  3. pytest-xdist-style sharding + independent-stage concurrency (GitLab/Jenkins job-parallelism) → Brief B. Doesn't cut total compute — it trades machine/core count for wall-clock time — but it's cheap, doesn't touch correctness (same work, just concurrent), and is the most "just turn it on" of all five leads if the gate is CPU-bound and idle cores exist. Directly matches Brief B's "parallelize scenarios across cores; split spec-pack vs scenarios to run concurrently."

  4. Little's Law + Theory of Constraints/Drum-Buffer-Rope together → Brief B + C's theoretical spine. These aren't techniques to install, they're the proof that the round's own diagnosis is structurally sound and the sequencing rule for exploiting it: DBR says never starve the drum (gate), pace releases into it via a rope (Brief C's WIP limit = 1 in COMMIT), and protect it with a buffer; Little's Law (L = λW, foundational, forte confidence) says cutting per-item cycle time is the only lever that cuts WIP without cutting throughput — which is precisely the round's stated goal restated as a formula. Use these to justify the backlog ranking, not as something to "adopt" per se.

  5. LLMCompiler's Planner→TaskFetchingUnit→Executor pattern → Brief C (cross-item pipelining), the gap the round doc names as still open. Section 1c of the round doc already notes REVIEW‖RECKON‖GATE fan-out exists (SPEC-157) but cross-item pipelining (item N+1's PLAN/IMPLEMENT overlapping item N's GATING) doesn't. LLMCompiler's explicit "identify independent vs interdependent tasks, dispatch the independent ones concurrently" is the same shape one level up — plan/implement(N+1) has no data dependency on gate(N) as long as footprints are disjoint (the round's own stated constraint). Confidence moderada (benchmarked on tool-calling, not build pipelines, so the specific speedup numbers don't transfer — only the architecture pattern does).

Watch, not now: "Speculative Actions" (arXiv 2510.04371) and the broader speculative-decoding literature are the closest frontier match to Brief B's "run the gate speculatively while review/reckon proceed" — same lossless-if-verified structure — but it's a single Oct-2025 preprint (prototipo maturity, not yet cross-validated), and the authors' own caveat ("coordinating multiple execution streams adds system complexity") is exactly the risk SPEC-137's gate-hold isolation exists to prevent. Worth a follow-up round once it's had more scrutiny, not a Deliver-phase pick today.

Unresolved / explicitly flagged as unverifiable this round: the bibliographic origin of the term "Drum-Buffer-Rope" itself (Front 4, TOC row) — my sources disagree on which Goldratt book coined the name — and the exact fingerprint-hash mechanics of Turborepo specifically (Front 1) I could not confirm by direct fetch, only by search-snippet synthesis. Both are registered as moderada rather than forte above rather than guessed into false confidence.
