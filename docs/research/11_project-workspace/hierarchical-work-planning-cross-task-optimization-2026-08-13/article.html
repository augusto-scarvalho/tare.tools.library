Hierarchical Work Planning & Cross-Task Optimization

Pesquisa científica e exploratória sobre backlog-as-projection, Work hierárquico, logical→physical planning, packetização, scheduling multi-task, liveness, loops, invalidation e rolling-horizon planning para o tare.tools Agent Operating System.

Scope

01

Resumo executivo

Esta pesquisa consolida uma hipótese arquitetural que emergiu da evolução do tare.tools: planejamento de trabalho agêntico é melhor tratado como otimização hierárquica sobre um modelo durável de Work do que como uma fila de backlog ou como três planners independentes. O backlog torna-se projection; o Work preserva identidade e lineage; o planejamento busca caminhos; a physicalization escolhe ordem, packetização, barriers e concorrência; Workflow materializa trabalho bounded; Routing seleciona executores; Authority limita toda realização possível; Evidence e Attribution fecham o ciclo.

Backlog is a view. Work is durable. Planning searches feasible paths. Physicalization chooses realization. Workflow executes bounded work. Authority constrains every effect. Evidence tells us what happened.

A literatura clássica de HTN formaliza decomposição hierárquica e a distinção entre tarefas abstratas e ações executáveis [R1] [R2]; HDDL mostra o valor de uma linguagem comum sem acoplamento obrigatório a um único solver [R3]. Operations Research e CP-SAT oferecem mecanismos maduros para precedência, exclusividade de recursos e makespan [R8] [R9]. Workflow Nets trazem a exigência de soundness/liveness [R4]. Build systems e query optimizers oferecem as analogias mais férteis para invalidation incremental e logical→physical planning [R6] [R7].

Convergência recomendada. Não criar um Planning Plane. Criar uma projection hierárquica e passes de análise/otimização sobre contratos canônicos existentes, começando read-only/shadow, com late binding e invalidation seletiva.
02

Problemas e objetivos

2.1 Problemas observados

  • Backlogs lineares escondem dependências, alternativas, shared prerequisites, authority/evidence paths e custo de rework.
  • Prioridade declarada não equivale a urgência de scheduling; uma P3 pode bloquear várias P0.
  • Task-level independence pode coexistir com conflito físico em arquivos, resources, effects ou Authority.
  • Overseers podem paralelizar por disponibilidade de agentes, não por useful parallelism.
  • Refinement feito cedo demais envelhece; refinement feito tarde demais duplica arqueologia/context reconstruction.
  • Safety local pode destruir liveness global — motivação concreta dada pelo governance deadlock do próprio projeto.
  • Aprendizado sem lineage/attribution pode culpar o executor por erro de planning, packetization, validation ou environment.

2.2 Objetivos científicos e de arquitetura

  1. Formalizar uma visão hierárquica do Work sem criar ontology paralela.
  2. Separar logical work semantics de physical work realization.
  3. Derivar cross-task execution frontiers com constraints duras primeiro e trade-offs Pareto depois.
  4. Detectar liveness failures, loops, stagnation e oscillation em múltiplas escalas.
  5. Definir quando pré-computar estrutura e quando late-bind refinement/schedule.
  6. Transformar execução observada em evidência para calibrar estimates, cuts, topology e recovery.
  7. Preservar Authority-before-intelligence e conservative evolution.

Findings

04

Modelo hierárquico de Work e resolução progressiva

HTN planning fornece uma base formal importante: tarefas abstratas podem ser decompostas por métodos até ações primitivas executáveis [R1] [R2]. O tare.tools, porém, precisa adicionar bounded-context ownership, lineage, Authority, Evidence, Resources e multiple runtime owners — portanto HTN é inspiração/solver model, não canonical ontology.

Strategic Target ↓ Work / Task ↓ selective expansion Obligations / candidate subwork ↓ Implementation Packet / Workflow region ↓ Workflow nodes ↓ Execution attempts / effects / receipts

O mesmo Work pode ser node na resolução superior e subgrafo quando expandido. Isso permite rolling refinement: detalhes baixos para horizonte distante; contracts e footprints explícitos para READY/COMMITTED; physical bindings apenas no momento de execução.

HDDL lesson. A proposta de uma linguagem comum para hierarchical planning surgiu justamente para reduzir compromisso precoce com um planner específico [R3]. Para tare.tools, o equivalente deve ser ainda mais conservador: uma projection/interchange layer pode ser solver-neutral, mas não substitui Task/Workflow/Authority/Evidence contracts canônicos.
05

Logical Work versus Physical Work Plan

Query optimizers dão a analogia mais forte. O RelOptPlanner de Calcite transforma expressões em formas semanticamente equivalentes segundo regras e um cost model, e Volcano mantém conjuntos de expressões equivalentes com diferentes physical traits [R7]. O equivalente tare é:

Logical obligation G ├─ realization R1: A → B → C ├─ realization R2: A → (B || C) └─ realization R3: experiment E → choose(B,D) Same desired semantics ≠ same cost/risk/trust/resource profile

Essa distinção impede uma confusão crucial: T1 BEFORE T2 pode ser scheduling precedence temporária devido a conflito de arquivo, enquanto T2 REQUIRES T1 é uma relação semântica durável. O optimizer deve poder gerar physical plans sem poluir o Work Graph canônico com decisões transitórias.

Memo de alternativas

Volcano sugere um caminho para evitar rediscovery: manter candidate realizations memoizadas por objetivo lógico + assumptions + snapshot, com costs e traits recomputáveis. O memo é cache/projection, não truth; qualquer mudança material em dependencies/policy/evidence deve invalidá-lo.

06

Cross-task scheduling e Execution Frontier

Quando múltiplas Tasks entram em análise simultaneamente, surge um problema intermediário que não é roadmap nem workflow interno: escolher qual fronteira de Work ativar agora. Job-shop scheduling formaliza a combinação de precedência e exclusividade de recursos [R9]; CP trata feasibility antes de optimization [R8]. O tare acrescenta Authority, Evidence, context locality e cost-to-trust.

Hard relations

REQUIRES, Authority eligibility, exclusive resources, subject identity, effect conflicts.

Soft relations

Affinity, context locality, continuity, setup/changeover, preferred executor, cost.

Transient plan relations

BEFORE, BATCH_WITH, BARRIER_AFTER, OWNERSHIP_WINDOW, DEFER.

Priority inheritance

Uma Task de baixa prioridade que bloqueia uma P0 deve herdar scheduling urgency sem reescrever sua prioridade canônica. Isso evita starvation de prerequisites e preserva a semântica original.

Useful concurrency

Structural width pode ser grande e effective/economic width pequena após artifact/resource/authority/conflict costs. O scheduler deve poder deixar workers ociosos quando fan-out antecipado aumenta expected rework. Little's Law lembra que WIP e lead time estão estruturalmente relacionados [R5].

07

Packetização, delegação e boundaries de Work

Delegar não deve significar “spawn agent”. Deve significar cortar um subgrafo cuja boundary é justificável. Candidate packets podem ser avaliados por semantic closure, dependency closure, context closure, artifact/effect isolation, authority closure e independent acceptance.

Critérios e trade-offs de packetização, delegação e boundaries de Work
SinalFavorece manter juntoFavorece separar/delegar
Internal couplingaltobaixo
Boundary edgesmuitos/instáveispoucos/tipados/estáveis
Shared mutable artifactsaltobaixo/isolável
Context overlapaltobaixo ou especializado
Acceptanceinseparávelindependente
Critical-path gainnenhummaterial

Um SCC é, por padrão, candidato a permanecer junto ou a exigir um ciclo explicitamente quebrado antes da delegação. Fan-out deve ocorrer preferencialmente após estabilização de contract setters dominantes — o padrão freeze-before-fanout.

Vendor evidence confirma que breadth-first research beneficia-se de subtarefas independentes [R14]; por outro lado, os relatos de harnesses long-running indicam que decomposição muito rígida pode perder valor à medida que modelos melhoram [R16]. Portanto packetization precisa ser adaptive e empirically calibrated.

08

Análises de grafo que realmente agregam

Nem toda métrica de graph science merece virar feature. As de maior valor operacional nesta linha são:

Reachability & liveness

Reachable targets, unreachable prerequisites, SCC/condensation, blocker sets, min-cuts.

Criticality

Critical execution/trust/evidence paths, dominators, articulation points, bridges.

Parallelism

Topological layers, antichains/width, conflict graph, resource matching.

Portfolio value

Downstream reach, unlock/blocker centrality, assumption/evidence centrality.

Organization

Communities, boundary crossing, integration hotspots, core/periphery as evidence only.

Temporal

Churn, plan stability, edge age, epoch diffs, rework propagation.

A principal disciplina é separar exact graph-derived, derived after costs/state e semantically inferred then deterministically calculated. LLM-generated edges nunca devem parecer canonical apenas porque um algoritmo determinístico as processou.

09

Liveness, loops e progress semantics

Workflow Nets mostram que soundness é um problema formal distinto de “cada passo parece válido”; a literatura cobre deadlocks, livelocks e outras anomalias e também mostra que extensões expressivas podem tornar certas propriedades indecidíveis [R4]. Isso é um alerta para não tentar formalizar tudo em um único supermodelo.

Progress vector

{
  targetDistance,
  unresolvedRequirements,
  blockerSet,
  failingAcceptance,
  criticalPathRemaining,
  trustDistance,
  evidenceDistance,
  unknowns,
  risk,
  remainingCost
}

Loop detector deve procurar recorrência + ausência de progresso material, não repetição textual. Classes relevantes: retry/effect loop, fix-test plateau/oscillation, reroute churn, replan churn, tool/search stagnation, context rediscovery, delegation cycle, impossible join, governance-deny loop, research stagnation, audit-corrective recurrence e evolution oscillation.

Loop contracts. Ciclos intencionais devem declarar entry/exit, invariant, progress/ranking measure, budget, repeatable effects e on-stagnation behavior. Ciclos não declarados no compiled workflow devem ser findings/errors, não “autonomia”.
10

Staleness, invalidation e incremental recomputation

Build systems são a melhor analogia para refinement freshness. Bazel distingue declared e actual dependencies [R18]; Build Systems à la Carte mostra que diferentes sistemas podem ser decompostos e recombinados por propriedades [R6]; Buck2 Change Detector deriva targets potencialmente afetados por um change set [R19].

Para tare.tools, um planning artifact deve carregar PlanningBasis e DependencyFootprint conceituais: project/task/architecture/policy/evidence/git/graph/cost revisions, além de Tasks/Specs/code/Authority/resources realmente consumidos. Staleness deve ser tipada:

  • SEMANTIC_STALE
  • TOPOLOGY_STALE
  • SUBJECT_STALE
  • AUTHORITY_STALE
  • RESOURCE_STALE
  • EVIDENCE_STALE
  • COST_STALE

O princípio é precompute structure early; infer semantics progressively; bind execution late. A physical realization deve ser mais volátil que logical work semantics.

11

Incerteza, Value of Information e rolling horizon

Planejamento de longo prazo deve evitar falsa precisão. Nodes distantes carregam cost/duration envelopes, dominant risks e low-confidence relations; nodes próximos ganham obligations/acceptance/footprints. A regra aproxima-se de receding-horizon planning: planejar mais longe, comprometer apenas uma janela curta e reavaliar após evidence.

Epistemic work

Research/experiment/qualification podem ser modelados como work que muda crenças em vez de mudar diretamente o produto. A decisão correta pode ser “comprar informação antes de comprometer uma arquitetura irreversível”. Isto exige separar direct value de information/option value.

Adaptive planning depth

O sistema também pode decidir quanto pensar: deep graph refinement, architecture review ou experiment só são econômicos quando a expected decision improvement supera o planning cost. Essa linha vira ponte para metareasoning, mas não deve ser requisito do MVP.

12

Agentic planning: onde LLMs agregam e onde não

HTN+LLM recentes sugerem uma combinação interessante: ChatHTN usa decomposições aproximadas do LLM dentro de um processo simbólico que mantém soundness do plano gerado [R11]; trabalho subsequente explora generalização online de methods [R12] e LLM-generated heuristics para busca HTN [R13]. Estes resultados são promissores, mas ainda RESEARCH e em domínios controlados.

ADOPTLLM para semantic reconstruction, missing-work hypotheses, candidate decompositions e explanation.
ADAPTHTN/PDDL-style precondition/effect models como interchange/experimental solver adapters.
RETIREHeurística “large task → N agents” sem análise de coupling/constraints.
OPENLLM-generated planner heuristics e learned decomposition methods até termos evidence local, replay e qualification.

OpenAI e Anthropic também enfatizam orchestration/tracing/handoffs em suas plataformas [R17] [R14], mas isso não resolve Authority, Work lineage ou evidence semantics do tare.tools; são comparison surfaces.

Síntese: arquitetura conceitual resultante

Canonical Project / Work / Lineage │ ▼ Logical Work Projection │ ├─ deterministic structure passes ├─ semantic enrichment (proposed edges) ├─ liveness / blocker analysis └─ value / uncertainty annotations │ ▼ Candidate Plan Memo │ ▼ Feasibility / Pareto optimization │ ▼ Physical Work Plan (order, packets, barriers, frontier, concurrency) │ ▼ Workflow compilation │ ▼ Authority / Capability / Resources / Routing │ ▼ Execution → Evidence → Outcome → Attribution │ └──────────── feedback / calibration ──────┐ └→ next planning epoch

O “optimizer” não é Authority, não é Workflow runtime e não é Routing. Ele produz candidate physicalizations. O compiled plan precisa satisfazer proof obligations de lineage, reachability/liveness, authority/capability/resource feasibility, conflict handling, evidence closure, subject integrity, rollback/recovery, freshness e progress semantics.

Programa experimental recomendado

  1. Golden-query projection. Sem nova primitive: “why does W exist?”, “what blocks X?”, “what is on every path?”, “what can run concurrently?”
  2. Deterministic V0. Explicit edges + reachability/SCC/topological frontier/critical path.
  3. Authority Dependency SCC shadow. Dogfood sobre governance/evolution work.
  4. Cross-task scheduler shadow. Compare actual overseer ordering against precedence/conflict/locality schedule.
  5. CP-SAT adapter experiment. Small frontier only; hard constraints first; no execution rights.
  6. Packetization advisor. Predict boundary cost, then compare against observed handoffs/merge/rework.
  7. Incremental invalidation. Change a spec/code/resource fact and verify minimal affected planning set.
  8. Loop/stagnation detector. Replay existing workflow traces; classify convergence, plateau and oscillation.

Todo experimento deve registrar a diferença entre prediction, chosen action e observed outcome, preparando a linha de learning descrita no documento complementar.
