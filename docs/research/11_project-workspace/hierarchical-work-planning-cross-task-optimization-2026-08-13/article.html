Hierarchical Work Planning & Cross-Task Optimization

Scientific and exploratory research on backlog-as-projection, hierarchical Work, logical→physical planning, packetization, multi-task scheduling, liveness, loops, invalidation and rolling-horizon planning for the tare.tools Agent Operating System.

Scope

01

Executive summary

This research consolidates an architectural hypothesis that emerged from the evolution of tare.tools: agentic work planning is better treated as hierarchical optimization over a durable model of Work than as a backlog queue or as three independent planners. The backlog becomes a projection; Work preserves identity and lineage; planning searches for paths; physicalization chooses order, packetization, barriers and concurrency; Workflow materializes bounded work; Routing selects executors; Authority constrains every possible realization; Evidence and Attribution close the loop.

Backlog is a view. Work is durable. Planning searches feasible paths. Physicalization chooses realization. Workflow executes bounded work. Authority constrains every effect. Evidence tells us what happened.

The classical HTN literature formalizes hierarchical decomposition and the distinction between abstract tasks and executable actions [R1] [R2]; HDDL shows the value of a common language without mandatory coupling to a single solver [R3]. Operations Research and CP-SAT offer mature mechanisms for precedence, resource exclusivity and makespan [R8] [R9]. Workflow Nets bring the soundness/liveness requirement [R4]. Build systems and query optimizers offer the most fertile analogies for incremental invalidation and logical→physical planning [R6] [R7].

Recommended convergence. Do not create a Planning Plane. Create a hierarchical projection and analysis/optimization passes over existing canonical contracts, starting read-only/shadow, with late binding and selective invalidation.
02

Problems and goals

2.1 Observed problems

  • Linear backlogs hide dependencies, alternatives, shared prerequisites, authority/evidence paths and rework cost.
  • Declared priority is not the same as scheduling urgency; a P3 can block several P0s.
  • Task-level independence can coexist with physical conflict in files, resources, effects or Authority.
  • Overseers may parallelize based on agent availability, not on useful parallelism.
  • Refinement done too early goes stale; refinement done too late duplicates archaeology/context reconstruction.
  • Local safety can destroy global liveness — a concrete motivation given by the project's own governance deadlock.
  • Learning without lineage/attribution can blame the executor for a planning, packetization, validation or environment error.

2.2 Scientific and architecture goals

  1. Formalize a hierarchical view of Work without creating a parallel ontology.
  2. Separate logical work semantics from physical work realization.
  3. Derive cross-task execution frontiers with hard constraints first and Pareto trade-offs afterwards.
  4. Detect liveness failures, loops, stagnation and oscillation at multiple scales.
  5. Define when to precompute structure and when to late-bind refinement/schedule.
  6. Turn observed execution into evidence to calibrate estimates, cuts, topology and recovery.
  7. Preserve Authority-before-intelligence and conservative evolution.

Findings

04

Hierarchical Work model and progressive resolution

HTN planning provides an important formal basis: abstract tasks can be decomposed by methods down to executable primitive actions [R1] [R2]. tare.tools, however, needs to add bounded-context ownership, lineage, Authority, Evidence, Resources and multiple runtime owners — so HTN is an inspiration/solver model, not a canonical ontology.

Strategic Target ↓ Work / Task ↓ selective expansion Obligations / candidate subwork ↓ Implementation Packet / Workflow region ↓ Workflow nodes ↓ Execution attempts / effects / receipts

The same Work can be a node at the higher resolution and a subgraph when expanded. This enables rolling refinement: low detail for the distant horizon; explicit contracts and footprints for READY/COMMITTED; physical bindings only at execution time.

HDDL lesson. The proposal of a common language for hierarchical planning arose precisely to reduce early commitment to a specific planner [R3]. For tare.tools, the equivalent must be even more conservative: a projection/interchange layer can be solver-neutral, but it does not replace the canonical Task/Workflow/Authority/Evidence contracts.
05

Logical Work versus Physical Work Plan

Query optimizers give the strongest analogy. Calcite's RelOptPlanner transforms expressions into semantically equivalent forms according to rules and a cost model, and Volcano maintains sets of equivalent expressions with different physical traits [R7]. The tare equivalent is:

Logical obligation G ├─ realization R1: A → B → C ├─ realization R2: A → (B || C) └─ realization R3: experiment E → choose(B,D) Same desired semantics ≠ same cost/risk/trust/resource profile

This distinction prevents a crucial confusion: T1 BEFORE T2 may be temporary scheduling precedence due to a file conflict, while T2 REQUIRES T1 is a durable semantic relation. The optimizer must be able to generate physical plans without polluting the canonical Work Graph with transient decisions.

Memo of alternatives

Volcano suggests a way to avoid rediscovery: keep candidate realizations memoized by logical goal + assumptions + snapshot, with recomputable costs and traits. The memo is cache/projection, not truth; any material change in dependencies/policy/evidence must invalidate it.

06

Cross-task scheduling and Execution Frontier

When multiple Tasks enter analysis at the same time, an intermediate problem arises that is neither roadmap nor internal workflow: choosing which frontier of Work to activate now. Job-shop scheduling formalizes the combination of precedence and resource exclusivity [R9]; CP handles feasibility before optimization [R8]. tare adds Authority, Evidence, context locality and cost-to-trust.

Hard relations

REQUIRES, Authority eligibility, exclusive resources, subject identity, effect conflicts.

Soft relations

Affinity, context locality, continuity, setup/changeover, preferred executor, cost.

Transient plan relations

BEFORE, BATCH_WITH, BARRIER_AFTER, OWNERSHIP_WINDOW, DEFER.

Priority inheritance

A low-priority Task that blocks a P0 should inherit scheduling urgency without rewriting its canonical priority. This avoids starvation of prerequisites and preserves the original semantics.

Useful concurrency

Structural width can be large while effective/economic width is small after artifact/resource/authority/conflict costs. The scheduler must be able to leave workers idle when early fan-out increases expected rework. Little's Law reminds us that WIP and lead time are structurally related [R5].

07

Packetization, delegation and Work boundaries

Delegating should not mean “spawn agent”. It should mean cutting a subgraph whose boundary is justifiable. Candidate packets can be evaluated by semantic closure, dependency closure, context closure, artifact/effect isolation, authority closure and independent acceptance.

Criteria and trade-offs for packetization, delegation and Work boundaries
SignalFavors keeping togetherFavors separating/delegating
Internal couplinghighlow
Boundary edgesmany/unstablefew/typed/stable
Shared mutable artifactshighlow/isolatable
Context overlaphighlow or specialized
Acceptanceinseparableindependent
Critical-path gainnonematerial

An SCC is, by default, a candidate to stay together or to require an explicitly broken cycle before delegation. Fan-out should preferably occur after the dominant contract setters have stabilized — the freeze-before-fanout pattern.

Vendor evidence confirms that breadth-first research benefits from independent subtasks [R14]; on the other hand, the reports on long-running harnesses indicate that overly rigid decomposition can lose value as models improve [R16]. Therefore packetization needs to be adaptive and empirically calibrated.

08

Graph analyses that actually add value

Not every graph-science metric deserves to become a feature. The ones with the highest operational value in this line are:

Reachability & liveness

Reachable targets, unreachable prerequisites, SCC/condensation, blocker sets, min-cuts.

Criticality

Critical execution/trust/evidence paths, dominators, articulation points, bridges.

Parallelism

Topological layers, antichains/width, conflict graph, resource matching.

Portfolio value

Downstream reach, unlock/blocker centrality, assumption/evidence centrality.

Organization

Communities, boundary crossing, integration hotspots, core/periphery as evidence only.

Temporal

Churn, plan stability, edge age, epoch diffs, rework propagation.

The main discipline is to separate exact graph-derived, derived after costs/state and semantically inferred then deterministically calculated. LLM-generated edges must never look canonical just because a deterministic algorithm processed them.

09

Liveness, loops and progress semantics

Workflow Nets show that soundness is a formal problem distinct from “each step looks valid”; the literature covers deadlocks, livelocks and other anomalies and also shows that expressive extensions can make certain properties undecidable [R4]. This is a warning not to try to formalize everything in a single supermodel.

Progress vector

{
  targetDistance,
  unresolvedRequirements,
  blockerSet,
  failingAcceptance,
  criticalPathRemaining,
  trustDistance,
  evidenceDistance,
  unknowns,
  risk,
  remainingCost
}

A loop detector should look for recurrence + absence of material progress, not textual repetition. Relevant classes: retry/effect loop, fix-test plateau/oscillation, reroute churn, replan churn, tool/search stagnation, context rediscovery, delegation cycle, impossible join, governance-deny loop, research stagnation, audit-corrective recurrence and evolution oscillation.

Loop contracts. Intentional cycles must declare entry/exit, invariant, progress/ranking measure, budget, repeatable effects and on-stagnation behavior. Undeclared cycles in the compiled workflow must be findings/errors, not “autonomy”.
10

Staleness, invalidation and incremental recomputation

Build systems are the best analogy for refinement freshness. Bazel distinguishes declared and actual dependencies [R18]; Build Systems à la Carte shows that different systems can be decomposed and recombined by properties [R6]; Buck2 Change Detector derives targets potentially affected by a change set [R19].

For tare.tools, a planning artifact should carry a conceptual PlanningBasis and DependencyFootprint: project/task/architecture/policy/evidence/git/graph/cost revisions, plus the Tasks/Specs/code/Authority/resources actually consumed. Staleness must be typed:

  • SEMANTIC_STALE
  • TOPOLOGY_STALE
  • SUBJECT_STALE
  • AUTHORITY_STALE
  • RESOURCE_STALE
  • EVIDENCE_STALE
  • COST_STALE

The principle is precompute structure early; infer semantics progressively; bind execution late. The physical realization should be more volatile than the logical work semantics.

11

Uncertainty, Value of Information and rolling horizon

Long-term planning should avoid false precision. Distant nodes carry cost/duration envelopes, dominant risks and low-confidence relations; near nodes gain obligations/acceptance/footprints. The rule approximates receding-horizon planning: plan further ahead, commit only to a short window and reassess after evidence.

Epistemic work

Research/experiment/qualification can be modeled as work that changes beliefs instead of directly changing the product. The correct decision may be “buy information before committing to an irreversible architecture”. This requires separating direct value from information/option value.

Adaptive planning depth

The system can also decide how much to think: deep graph refinement, architecture review or experiment are only economical when the expected decision improvement exceeds the planning cost. This line becomes a bridge to metareasoning, but it should not be an MVP requirement.

12

Agentic planning: where LLMs add value and where they do not

Recent HTN+LLM work suggests an interesting combination: ChatHTN uses approximate LLM decompositions inside a symbolic process that preserves the soundness of the generated plan [R11]; subsequent work explores online generalization of methods [R12] and LLM-generated heuristics for HTN search [R13]. These results are promising, but still RESEARCH and in controlled domains.

ADOPTLLM for semantic reconstruction, missing-work hypotheses, candidate decompositions and explanation.
ADAPTHTN/PDDL-style precondition/effect models as interchange/experimental solver adapters.
RETIREThe “large task → N agents” heuristic without coupling/constraints analysis.
OPENLLM-generated planner heuristics and learned decomposition methods until we have local evidence, replay and qualification.

OpenAI and Anthropic also emphasize orchestration/tracing/handoffs in their platforms [R17] [R14], but that does not solve tare.tools' Authority, Work lineage or evidence semantics; they are comparison surfaces.

Synthesis: resulting conceptual architecture

Canonical Project / Work / Lineage │ ▼ Logical Work Projection │ ├─ deterministic structure passes ├─ semantic enrichment (proposed edges) ├─ liveness / blocker analysis └─ value / uncertainty annotations │ ▼ Candidate Plan Memo │ ▼ Feasibility / Pareto optimization │ ▼ Physical Work Plan (order, packets, barriers, frontier, concurrency) │ ▼ Workflow compilation │ ▼ Authority / Capability / Resources / Routing │ ▼ Execution → Evidence → Outcome → Attribution │ └──────────── feedback / calibration ──────┐ └→ next planning epoch

The “optimizer” is not Authority, is not the Workflow runtime and is not Routing. It produces candidate physicalizations. The compiled plan must satisfy proof obligations of lineage, reachability/liveness, authority/capability/resource feasibility, conflict handling, evidence closure, subject integrity, rollback/recovery, freshness and progress semantics.

Recommended experimental program

  1. Golden-query projection. No new primitive: “why does W exist?”, “what blocks X?”, “what is on every path?”, “what can run concurrently?”
  2. Deterministic V0. Explicit edges + reachability/SCC/topological frontier/critical path.
  3. Authority Dependency SCC shadow. Dogfood on governance/evolution work.
  4. Cross-task scheduler shadow. Compare actual overseer ordering against precedence/conflict/locality schedule.
  5. CP-SAT adapter experiment. Small frontier only; hard constraints first; no execution rights.
  6. Packetization advisor. Predict boundary cost, then compare against observed handoffs/merge/rework.
  7. Incremental invalidation. Change a spec/code/resource fact and verify minimal affected planning set.
  8. Loop/stagnation detector. Replay existing workflow traces; classify convergence, plateau and oscillation.

Every experiment must record the difference between prediction, chosen action and observed outcome, preparing the learning line described in the companion document.
