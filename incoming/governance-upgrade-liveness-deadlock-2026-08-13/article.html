Deadlock de governança e liveness de evolução no tare.tools: arqueologia, causa-raiz e arquitetura de recuperação

Estudo arqueológico e comparativo do ciclo de governança que tornou mudanças tecnicamente qualificadas difíceis de publicar, validar em GitHub CI e landar no tare.tools. A investigação reconstrói a evolução de Validation, Reckon, Mutation, Audit, CommitAuthority, proof authority e TrustedVerifier; modela a circularidade como um bootstrap authority dependency cycle; cruza o caso com deadlocks, secure bootstrap, supply-chain provenance e failure modes de sistemas agênticos; e propõe, sem ratificação arquitetural, Recovery Bridge → Trusted Control Plane → Incumbent-to-Incumbent Evolution como caminho de recuperação compatível com os princípios de authority-before-intelligence, evidence-first e migração incremental do tare.tools.

1. Scope

The incident emerged from incremental governance hardening: Validation → Reckon → Mutation → Audit → CommitAuthority → proof/process receipts → strict no-waiver → TrustedVerifier. Each step closed a real threat; their composition eventually required a production trust root to authorize changes needed to build that same root.

The operational symptom was not merely red CI: evidence-rich candidates could not reliably become exact GitHub CI subjects and land protected PRs. At cutoff, main/tree were 477bea0d.../a8d2cb7f...; PR #16 (46d97a17...) and #13 (eb08cd622...) were draft/open; Issue #23 preserved base 8d040aac... plus audited patch digest ef89bb90...; TG-01A corrective existed but its closure audit was pending.

Questions: how did the authority cycle form; why did local correctives not break it; how should evidence acquisition differ from promotion; which bootstrap/control-plane architecture preserves safety and upgrade liveness; and what termination rule should stop agentic corrective loops when global landing progress stalls?

2.1 Trust Genesis falsifier

TG-01A independently showed that a re-sealable strictAuthorityDigest proves self-consistency, not actual trusted execution. A valid anchor could coexist with fabricated execution claims when TrustedVerifier.validate()/GovernanceCampaign.run_leg() had not produced the evidence. Thus:

integrity(hash(payload)) ≠ producer provenance
≠ process-bound execution provenance ≠ promotion authority

2.2 Comparative evidence

Coffman/Tarjan motivate circular-wait/SCC analysis; UEFI Setup Mode and RFC trust-anchor work distinguish bootstrap from steady state; TUF makes trusted root N participate in N+1; Kubernetes uses limited bootstrap credentials then removes them; SLSA places provenance production in a trusted control plane outside the subject; GNU Mes minimizes rather than denies the bootstrap seed. Empirical architecture-smell work shows cycles can accrete over releases. Agent research (Hou 2026; Cemri 2025; Wang 2026; Huang 2023) supports a workflow framing: feedback loops and locally good decisions need effective global termination/progress conditions. It does not support blaming Fable/LLMs for this incident; the primary failure is system design/orchestration.

3. Findings and proposed direction

3.1 Bootstrap Authority Dependency Cycle

F=needed fix → C=CommitAuthority → V=eligible Validation
→ T=TrustedVerifier → G=Genesis → F

Improving an edge can remain locally correct while preserving the SCC. The cycle disappears only when a dependency is reoriented to already-legitimate authority or a narrow audited case-base crosses the transition.

3.2 Governance Upgrade Liveness

PROPOSED GUL:
For authority regime N and admissible successor N+1,
there MUST exist a finite, auditable, bounded path by which
authority legitimate under N can materialize, evaluate and
transition to N+1 without requiring authority only present in N+1.

Root cause: safety grew while this upgrade-liveness property, learned during SPEC-137 migration, was never carried forward as a canonical invariant.

3.3 Evidence Acquisition Non-Promotion

Materialize exact candidate for evidence:
MUST NOT imply trust or promotionEligibility;
MUST NOT mutate staging/main;
MUST bind exact subject + effect;
MAY enable CandidateCI + independent audit.

3.4 Alternatives

Stable-incumbent controller and verifier-proof/independent-consumer are strong steady-state components but do not by themselves create the first transition. TG-01A→B→C→Genesis before any candidate publication preserves the SCC. Generic --no-verify/policy relaxation is an unbounded bypass; permanent Bootstrap Authority creates a durable second root. The selected direction therefore composes a temporary Recovery Bridge with a subsequent Trusted Control Plane and incumbent-mediated evolution.

3.5 Recovery Bridge — PROPOSED

Owner Authority → exact scoped Permit
→ candidate materialization → non-authoritative candidate ref
→ CandidateCI → independent audit → exact DEV transition Permit
→ normal PR / IntegrationCI → protected landing

No RecoveryAuthority/GitHubAuthority/store is introduced. The Permit binds base/tree, patch or expected candidate tree, ref namespace, old OID/CAS, expiry, single-use consumption, owner decision and auditor locator. main/staging/rulesets/trust stores/tags/releases remain outside its ceiling. Candidate publication remains trust=UNKNOWN/UNQUALIFIED, promotionEligible=false.

3.6 CandidateCI versus IntegrationCI

CandidateCI asks “do these exact candidate bytes pass?”; IntegrationCI asks “do they pass as integrated against this base?”. They are distinct Evidence Families with distinct staleness.

3.7 Simulation for #23/#16/#13

#23 exact candidate K → required-OS CandidateCI(K) → independent audit
→ bounded DEV transition → reconcile PR #16 → IntegrationCI/staging
→ normal promotion/merge → requalify PR #13 → IntegrationCI → decision

Recovery ends before staging and therefore cannot replace protected promotion. Qualitative engineering priors used only for architecture comparison were: #23 materialization ~95%; exact CandidateCI acquisition ~90–95%; #23 3-OS green ~85–95%; #16 lineage ~90–95%; #16→staging ~75–85%; broader #13 after new base ~60–75%. These are not calibrated probabilities or guarantees.

3.8 Trusted Control Plane and N→N+1 — PROPOSED

After recovery: first executed byte incumbent-fixed; controller/verifier/recorder/consumer outside candidate; process-bound receipts; decision/promotion binding; runtime/dependency identity; confinement; release freshness; strict eligibility only with real preconditions. Then evolution becomes trusted incumbent N + qualified N+1 → TransitionReceipt(old=N,new=N+1) → incumbent N+1. Recovery must be retired; reuse after steady-state authority blocks and emits critical evidence.
