02 · causalidade e dependências

Root cause e modelo formal do deadlock

Formaliza o bootstrap authority dependency cycle como uma SCC, separa gatilho de causa sistêmica e propõe invariants de upgrade liveness, evidence acquisition e judge independence.

FACTSPROPOSED invariantsCutoff: 2026-08-13 19:37 BRTRepo: universal-agent-harness-prototype

1. O nome correto do problema

O incidente parece um deadlock porque progresso está bloqueado por dependências circulares, mas não é um deadlock clássico de recursos. É mais precisamente um bootstrap authority dependency cycle: uma regra de autoridade exige uma condição que só pode ser criada por uma mudança sujeita à própria regra.

Distinção: Coffman et al. tratam deadlocks de processos/recursos e identificam circular wait como uma condição estrutural clássica. Nosso caso compartilha a topologia de espera circular, mas não todos os requisitos de resource deadlock. A analogia útil é topológica; a classificação precisa é bootstrap/cyclic-authority deadlock.

2. Grafo de dependência de autoridade

F = instalar correção de Validation / Genesis
C = CommitAuthority autorizar commit
V = staged Validation elegível
T = TrustedVerifier legítimo
G = Genesis / primeira root legítima

F → C → V → T → G → F

SCC = {F, C, V, T, G}
nenhum nó possui predecessor confiável fora do SCC
capaz de fornecer o caso-base.

Em termos de teoria de grafos, isso é uma strongly connected component (SCC): cada nó relevante é alcançável a partir dos outros. Tarjan mostrou que SCCs em grafos dirigidos podem ser identificadas em tempo linear. Para tare.tools, o valor não é o algoritmo em si, mas o modelo: uma evolução de governança não pode introduzir uma SCC de autoridade sem um caso-base ou aresta de escape explicitamente autorizada.

4. A causa sistêmica mais profunda: perda de upgrade liveness

Proposed invariant — Governance Upgrade Liveness (GUL)

PROPOSED Para toda authority epoch N e toda mudança aprovada destinada a produzir N+1, deve existir ao menos um caminho finito P, autorizado por N ou por um bootstrap authority externo e limitado, pelo qual N+1 possa ser:

identified → materialized → evidenced → independently judged → activated

sem exigir como pré-condição autoridade que só existe em N+1.

O SPEC-137 original já possuía o embrião desse invariant: migration window, owner opt-in e escape observável. O projeto inclusive desabilitou uma habilitação prematura e exigiu liveness antes de reativar o gate. O que faltou foi tornar essa propriedade monotônica: cada novo hardening deveria provar não apenas safety, mas também que o upgrade path continuava alcançável.

6. “Hash binding proves integrity, not producer provenance”

Esta frase é a assinatura técnica do incidente. Ela aparece conceitualmente em duas épocas:

  1. Round ER (08/08): derived logs/VERDICT não podem ser a raiz; controller-owned process receipt precisa provar a execução.
  2. TG-01A v1 (13/08): strictAuthorityDigest podia ser re-selado junto com claims fabricadas. O consumer verificava consistência interna, não que GovernanceCampaign/TrustedVerifier realmente tivessem produzido o resultado.

O finding do TG-01A não foi um bug novo: foi uma recorrência do mesmo princípio de provenance em outro nível porque o finding histórico não tinha se transformado em invariant canônico.

7. O segundo invariant ausente: evidence acquisition não é promotion

Proposed invariant — Evidence Acquisition Non-Promotion

PROPOSED Tornar um Candidate endereçável e executável por uma infraestrutura de evidence não confere trust, activation ou promotion authority.

Candidate materialization
        ≠ Candidate publication
        ≠ Candidate promotion

Cada efeito requer seu Permit e produz seu EffectReceipt. Só promotion requer proof/authority do nível de promoção.

O próprio Git já separa esses efeitos: write-tree/commit-tree criam identidade de objeto; update-ref move uma referência; merge/promote altera uma lane protegida. Nosso modelamento havia achatado essa separação.

8. O terceiro invariant: o candidate não controla o judge

Judge-Determinism-Under-Candidate-Mutation: para candidate C, o veredicto deve depender apenas da identidade congelada de C e de bytes de autoridade fixados por uma autoridade anterior/independente. C não pode mudar verifier, controller, parser, proof binding, consumer ou CommitAuthority para o julgamento de C.

Essa regra foi formulada no handoff de 10/08. O trusted-invocation follow-up mostrou que até o hook/bootstrap inicial precisava ser incumbent-fixed: pinning tardio não basta se o primeiro byte pode escolher não pinar.

10. Por que “--no-verify” não é a solução

O sistema sempre teve escapes em fases anteriores, mas a arquitetura ratificada não os transforma em solução. Um bypass oculto:

  • não distingue subject autorizado de qualquer outra mudança;
  • não prova old→new identity;
  • não é single-use por construction;
  • mistura “commit exists” com “promotion allowed”;
  • cria pressão para reutilizar o bypass.

Recovery Bridge é diferente: é uma transição explícita, subject-bound, purpose-bound, evidence-producing, revogável e com effect ceiling que termina antes de staging.

Root cause statement

A causa-raiz sistêmica foi a ausência de um invariant de liveness de evolução da própria governança. O harness aumentou progressivamente safety e proof authority, mas não exigiu que cada novo authority gate demonstrasse uma transição finita a partir do incumbent anterior. Quando strict production trust passou a ser pré-condição da mesma evolução necessária para construí-lo, formou-se uma SCC de autoridade. O problema foi amplificado pela falta de separação semântica entre publicar um candidate para evidence e promover/trustar esse candidate.
