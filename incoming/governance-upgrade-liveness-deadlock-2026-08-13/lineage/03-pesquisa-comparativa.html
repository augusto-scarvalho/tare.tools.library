Pesquisa comparativa: deadlocks, bootstrap e loops de agentes

Cruza o incidente com deadlocks clássicos, cyclic dependencies, secure boot, trust-anchor initialization, TUF, Kubernetes, SLSA, bootstrappable builds e pesquisas recentes sobre feedback loops e falhas de planejamento em agentes LLM.

RESEARCHCutoff: 2026-08-13 19:37 BRTRepo: universal-agent-harness-prototype

1. Como comparar sem falsa equivalência

Não existe um único campo que tenha “o mesmo bug” do tare.tools. A análise combina quatro famílias: deadlock/ciclos em grafos, secure bootstrap/trust-anchor initialization, software bootstrapping e architectural cycles, e agentic feedback loops. Cada uma explica uma dimensão diferente.

2. Deadlock clássico e SCCs

Coffman et al. (1971)

O paper clássico enquadra deadlocks como “deadly embrace” e sistematiza condições de espera circular em sistemas multiprogramados.

Aplicação: nossa topologia tem circular wait, mas não é um resource deadlock completo. Use a teoria como lente, não como identidade.

Tarjan (1972)

Strongly connected components dão um teste objetivo para ciclos dirigidos.

Aplicação: Authority Dependency Graph pode ser analisado por SCC antes de ratificar um hardening.

ADAPT: introduzir uma análise de SCC em dependências de autoridade/prova/migração, possivelmente sobre Graphify/AST + contracts. Não transformar toda dependência circular em erro: o blocker é SCC sem caso-base/escape autorizado.

3. Secure Boot: primeiro enrollment é um estado diferente

UEFI 2.11 define Setup Mode quando não existe Platform Key. Nesse estado, firmware não exige autenticação para modificar a PK; após enrollment bem-sucedido, transiciona imediatamente a User Mode e modificações futuras exigem autenticação pela PK corrente.

no root
  → SETUP MODE
  → enroll initial root
  → USER MODE
  → authenticated updates

ADOPT: initialization/recovery é semanticamente diferente do steady state. RETIRE: fingir que a primeira root deve ser autenticada pelas regras que ela própria cria.

4. RFC 6024 / RFC 9718: trust anchor é um caso-base externo

RFC 9718 define trust anchor como uma entidade cuja confiança é assumida, não derivada; a decisão de confiar ocorre fora do sistema que depende dela. RFC 6024 diz que, idealmente, mecanismos out-of-band são necessários apenas na inicialização do trust-anchor store e que depois a gestão deve reduzir essa dependência.

ADOPT: Recovery Bridge como caso-base owner-authorized; ADAPT: depois converter para in-band incumbent succession.

5. TUF: bootstrap externo, evolução N→N+1 interna

TUF exige que clientes já tenham uma trusted root inicial. Depois, para atualizar root N→N+1, a nova root precisa satisfazer threshold da root antiga e threshold da própria nova root; versões monotônicas e expirations defendem rollback/freeze.

FIRST ROOT: out-of-band

steady state:
trusted root N
   +
new root N+1 self-consistency/threshold
   ↓
trusted line of continuity
   ↓
root N+1

ADOPT: é a principal inspiração para Incumbent-to-Incumbent Evolution. O candidate nunca deve ser suficiente para autorizar a si próprio.

6. Kubernetes: bootstrap credential é limitada e descartável

No TLS bootstrap, kubelet usa um token limitado para criar/obter CSR; recebe credencial normal; kubeadm apaga bootstrap-kubelet.conf quando a transição termina. A documentação recomenda RBAC que limita tokens estritamente à provisão.

ADOPT: Recovery Permit com escopo estreito e condição de morte. O bootstrap não é “super-admin eterno”.

7. SLSA: provenance pertence ao control plane, não ao subject

SLSA define control plane como componente de build que orquestra execução e produz provenance, fora do controle do tenant. A threat model mostra que provenance forjada é mitigada quando o control plane — não o worker controlado pelo tenant — gera os campos confiados.

candidate/tenant controls SUBJECT
          ↓
trusted control plane controls PROVENANCE
          ↓
independent verifier consumes expectations

ADOPT: Trusted Control Plane. Esta é também a explicação externa mais direta do falsifier TG-01A: um JSON re-selável produzido pelo próprio subject não se torna provenance por ter hash.

8. Software bootstrapping: reduzir o seed, não fingir que ele não existe

GNU Mes/Bootstrappable Builds parte do problema dos bootstrap binary seeds. A estratégia é reduzir o seed confiado e tornar o crescimento reprodutível/auditável, não eliminar magicamente o caso-base.

ADAPT: minimizar o TCB do Recovery Bridge: Git + exact object identities + owner decision + auditor; depois reduzir/remover a exceção.

9. Cyclic dependencies como architecture smell

Estudo empírico de Gnoyke, Schulze e Krüger (JSS 2024) acompanha 485 releases de 14 sistemas e observa que cyclic-dependency families podem crescer/mesclar em estruturas complexas; mudanças ripple através do ciclo e dificultam manutenção/deployment independente.

Isso descreve bem o fenômeno de accretion observado aqui: não criamos uma mega-SCC de uma vez. Dependências de Validation, Reckon, Mutation, Audit, CommitAuthority e TrustedVerifier foram se fundindo até a governança depender de seu próprio futuro.

10. AI/LLM: o que a evidência realmente permite afirmar

Importante: não há evidência de que “Fable causou o deadlock porque IA toma decisões cíclicas”. A causa é arquitetural e de workflow. A literatura de agentes ajuda a explicar por que um processo multiagente com correções locais pode permanecer num feedback path sem detectar que o objetivo global parou de avançar.

10.1 Infinite Agentic Loops — Hou et al. (2026)

O paper define IALs como feedback paths em que model calls, tools, workflow transitions ou handoffs repetem sem bound efetivo. IAL-Scan constrói um Agentic Loop Dependence Graph (ALDG) e verifica se feedback paths alcançam operações custosas/state-growing sem um limite que realmente cubra o controller. Em 6.549 repositórios, 68 falhas foram confirmadas em 47 projetos, com 91,9% de precisão reportada.

Analogia tare.tools: implement→audit→correct→audit era um feedback path legítimo e bounded em cada packet, porém não havia bound de nível arquitetural do tipo “pare se a distância até landing não diminuir” ou “pare se a próxima correção depende da autoridade que a própria correção tenta criar”.

10.2 Why Do Multi-Agent LLM Systems Fail? — Cemri et al. (2025)

O estudo organiza 14 failure modes em três grupos: specification/system design, inter-agent misalignment e task verification/termination. Isso reforça uma leitura importante do nosso incidente: a falha pode morar na orquestração, mesmo quando implementer e auditor individualmente fazem bom trabalho.

10.3 Why Reasoning Fails to Plan — Wang et al. (2026)

O paper argumenta que step-wise reasoning pode induzir uma política localmente gulosa: escolhas localmente boas criam compromissos precoces que se amplificam ao longo do horizonte. Isso é uma analogia forte para nosso security ratchet: cada novo falsifier pedia uma correção racional local, mas não havia lookahead explícito sobre a alcançabilidade do estado final “PR landado”.

10.4 Intrinsic self-correction pode degradar — Huang et al. (2023)

Em tarefas de reasoning, o estudo encontra que LLMs podem ter dificuldade para auto-corrigir sem feedback externo e às vezes pioram após self-correction. Nosso processo tinha auditor independente, portanto não é “intrinsic self-correction”; ainda assim a lição útil é evitar assumir que iterar crítica→correção, por si só, converge.

11. A intervenção humana como controle de nível superior

O owner percebeu que a função objetiva havia derivado: “governança cada vez mais correta” estava vencendo “voltar a desenvolver e landar”. O pedido para parar e investigar funcionou como uma meta-level termination condition que o workflow não possuía.

Isso sugere uma regra futura para sistemas agentes:

PROPOSED Progress Governor: a cada corrective round, medir quais blockers do objetivo operacional foram removidos/adicionados. Se uma sequência forma SCC, não reduz o blocker set ou introduz autoridade futura como pré-condição de si mesma, escalar para arquitetura/owner em vez de emitir automaticamente outro implementation packet.

13. Ponteiros de estudos futuros

  1. Authority Dependency Graph / Bootstrap SCC detector: Graphify + AST + SPEC ownership; distinguir cycles legítimos de authority SCCs sem seed.
  2. TLA+/Alloy: modelar single-use Permit, exact old→new CAS, crash/restart, replay e revocation.
  3. Trusted invocation slice-0: first byte incumbent-fixed em Windows/POSIX/CI.
  4. CandidateCI vs IntegrationCI: formalizar como Evidence Families, não jobs ad hoc.
  5. TUF-style verifier/policy epoch rotation: threshold/continuity/freeze/rollback semantics.
  6. SLSA/in-toto mapping: o que reutilizar em provenance sem transformar protocolo em boundary arquitetural.
  7. Progress Governor para agentes: blocker-set delta, SCC detection, horizon-aware lookahead e owner escalation.
  8. Transparency log: authorization/effect receipts append-only para detectar abuso de recovery permits.
  9. Reproducible bootstrap / Diverse Double Compilation: reduzir confiança no executable do bootstrap/control plane.
