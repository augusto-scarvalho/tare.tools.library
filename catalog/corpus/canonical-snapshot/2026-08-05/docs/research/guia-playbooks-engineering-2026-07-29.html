    Engenharia de Playbooks para Harnesses Multiagênticos

    Como modelar, compilar, injetar, executar, avaliar e evoluir instruções de agentes especializados com eficiência de contexto, governança determinística e portabilidade entre vendors.

    Projeto-alvoMulti Agent Harness

    Conclusão central

    Playbooks devem continuar existindo como fontes humanas versionadas — Markdown, YAML, schemas, políticas, scripts e referências — mas o agente deve consumir um playbook efetivo compilado para a tarefa corrente. Para subagentes, o runtime deve derivar uma cápsula ainda menor, o Spawn Envelope, e paginar somente o frame ativo do procedimento.

    1 Como usar este documento

    Este guia transforma a pesquisa sobre papéis, SOPs, skills, prompt programming, context engineering e runtime enforcement em uma proposta implementável para o harness. Ele assume a arquitetura de projeto já definida: uma camada intermediária entre modelos, agentes, tools, repositórios e usuários, com um intelligence plane probabilístico contido por um control plane determinístico. [1]

    Para arquitetura

    Leia as seções 3 a 7: metamodelo, compilador, IR, lockfile e runtime pager.

    Para prompts e custo

    Leia as seções 8 a 11: spawn, orçamento, caching, pruning e compressão.

    Para implementar

    Leia as seções 12 a 17 e os apêndices: schemas, código, evals e roadmap.

    Sobre atualidade: documentação de vendors e preprints de 2026 podem mudar rapidamente. O documento marca fontes como “documentação viva”, “preprint recente” ou “referência consolidada” e propõe uma política de revalidação.

    2 Definições e modelo mental

    2.1 Playbook não é sinônimo de prompt

    Na prática atual, “playbook” é um termo guarda-chuva. A literatura usa SOP, role profile, agent skill, instruction set, workflow, scaffold, policy, prompt program e orchestration prompt. MetaGPT consolidou a ideia de codificar SOPs em sequências de prompts; MASAI e AgentCoder mostraram que papéis úteis possuem estratégias, tools e feedback distintos; SWE-agent mostrou que a interface oferecida ao agente altera o comportamento tanto quanto a instrução textual. [2][3][4][5]

    Playbook-fonte ≠ Prompt final ≠ Workflow ≠ Política ≠ Estado de execução

    3 Evolução do padrão: de persona para programa operacional

    2023

    SOPs e papéis

    MetaGPT e AgentCoder codificam processos humanos e separam implementação, testes e execução. A contribuição durável é a separação de responsabilidades e feedback executável, não a teatralização dos cargos. [2][3]

    2024

    Estratégias e interfaces

    MASAI usa subagentes com objetivos e estratégias diferentes; SWE-agent demonstra que comandos, edição e observações formam uma Agent-Computer Interface que condiciona o desempenho. [4][5]

    2025

    SOP estruturado, policy e context engineering

    SOP-Agent representa procedimentos como pseudocódigo/grafo; AgentSpec transforma restrições em regras executáveis; vendors passam a enfatizar progressive disclosure, contexto mínimo e workflows determinísticos quando possível. [41][43][27][28]

    2026

    Compilação, benchmarks e economia

    Compile, Then Page e SkillSmith estudam compilação de SOPs/skills; AOrchestra trata o agente criado como uma composição de Instruction, Context, Tools e Model; SkillsBench, SWE-Skills-Bench e SkillReducer medem utilidade e custo. [42][44][47][48][49][50]

    Padrão destilado: especialização útil muda o contrato operacional — inputs, tools, estratégia, authority, artefatos, verificação e parada — e não apenas o texto “você é especialista”.

    5 Arquitetura do Playbook Compiler

    5.1 Compilador, linker e renderer

    O componente proposto combina três responsabilidades tradicionais:

    Compiler

    Parseia, normaliza, tipa, valida e converte fontes em IR.

    Linker

    Resolve versões, dependências, precedência, imports e capabilities.

    Renderer

    Produz prompts, schemas, tool bindings e payloads específicos por vendor.

    GitHub Agentic Workflows é o exemplo industrial mais claro de fonte humana separada do artefato executável: Markdown é compilado em .lock.yml após parsing, validação, construção de jobs, resolução de dependências e hardening. [13][14] Compile, Then Page e SkillSmith mostram a mesma tendência em pesquisa: compilar procedimentos ou skills antes da execução, em vez de reinjetar documentos crus em todo turno. [42][47]

    5.2 Pipeline recomendado

    Parse
    →
    Normalize
    →
    Resolve
    →
    Type check
    →
    Policy check
    →
    Lowering
    →
    Lock
    1. Parse: Markdown frontmatter, YAML, JSON Schema e policy modules.
    2. Normalize: converter sinônimos, defaults e versões para uma AST canônica.
    3. Resolve: selecionar papel, procedimento, skills, projeto e paths afetados.
    4. Type check: verificar handoffs, state schemas, tool arguments e outputs.
    5. Policy check: aplicar deny-overrides, approvals e budgets antes do modelo.
    6. Lowering: gerar workflow graph, prompt plan, capabilities e adapters.
    7. Lock: produzir manifesto com hashes, proveniência e configuração efetiva.

    7 Compilação do prompt inicial: Spawn Envelope

    7.1 Por que não copiar o contexto do pai

    AOrchestra compara explicitamente subagentes com contexto nenhum, contexto completo e contexto curado; sua abstração cria cada executor como uma tupla de instrução, contexto, ferramentas e modelo. PerspectiveGap mostra que decidir qual informação pertence a qual papel é uma capacidade distinta e ainda difícil. AgentSpawn investiga transferência seletiva de memória durante o spawning. [44][45][46]

    Anti-pattern: spawn_prompt = parent_transcript + all_tools + full_playbook. Isso duplica custo, propaga ruído, amplia prompt injection e confunde ownership.

    7.2 Estrutura recomendada

    SpawnEnvelope =
    RoleKernel
  + DelegationCapsule
  + RelevantBindingState
  + CapabilityIndex
  + CurrentExecutionFrame
  + ReturnContract
    BlocoDeve conterNão deve conter
    Role KernelMissão, ownership, authority e fronteiras.Biografia e melhores práticas enciclopédicas.
    Delegation CapsuleObjetivo local, critérios, non-goals e dependências.Conversa inteira do overseer.
    Binding StateFatos confirmados, decisões vinculantes e riscos ativos.Hipóteses refutadas e logs crus.
    Capability IndexTools carregadas, descobríveis e proibidas.Catálogo inteiro de schemas.
    Current FramePasso atual, instrução imediata, saída esperada.Todo o workflow futuro em detalhes.
    Return ContractSchema, evidência, stop e escalation.Relato narrativo sem estrutura.

    - retry não duplica o botão
    - navegação por teclado permanece funcional

    - o problema exige falha seguida de retry
    - PaymentForm controla pending
  bindingDecisions:
    - usar o design system existente
    - não introduzir estado global

  - uri: repo://src/frontend/payment/PaymentButton.tsx
  - uri: artifact://TASK-142/reproduction.md

  loaded: [repository.read, repository.search, test.run]
  discoverable: [repository.edit, browser.inspect, accessibility.scan]
  denied: [production.deploy, network.external, secrets.read]

  step: inspect
  instructions:
    - localize owners de pending, retry e submission
    - não edite nesta etapa

  finalSchema: implementation-result/v2
  escalateWhen: [backend-change-needed, protected-path, policy-conflict]

    7.4 Layout cache-aware e attention-aware

    Prefixo estático e cacheávelpapel, authority, políticas, tools comuns
    Corpo dinâmicotarefa, fatos, artefatos e referências
    Frame terminalpasso atual, output, stop e escalation

    OpenAI e Anthropic exigem prefixos idênticos para maximizar cache hits: conteúdo estático deve vir primeiro e o variável depois. Entretanto, tokens cacheados continuam ocupando a janela; caching reduz prefill, latência e custo, mas não substitui seleção ou pruning. [24][31][32]

    9 Estratégia de redução de tokens

    9.1 Ordem recomendada

    1. Deduplicar: remover regras repetidas, backstory e exemplos equivalentes.
    2. Compor seletivamente: carregar apenas papel, procedimento, domínio e paths aplicáveis.
    3. Referenciar: substituir documentos extensos por URIs recuperáveis.
    4. Descobrir tools sob demanda: expor um índice pequeno e carregar schemas quando usados.
    5. Filtrar observações: resumir logs, listas e resultados no ambiente determinístico.
    6. Materializar estado: manter decisões e artefatos fora da transcrição.
    7. Remover trajetória expirada: descartar outputs redundantes ou já substituídos.
    8. Pruning task-aware: preservar sintaxe, IDs e relações necessárias.
    9. Compressão semântica: último recurso para prosa e documentação narrativa.

    9.2 O que a evidência recente mostra

    TrabalhoTécnicaResultado reportadoCuidado

    SWE-PrunerPruning de linhas guiado por objetivo da tarefa.23–54% de redução em tarefas agênticas reportadas.Precisa preservar estrutura de código. [53]

    9.3 Conteúdo protegido contra compressão

    Preservar literalmente

    • Policies e proibições
    • Acceptance criteria
    • Tool names e argumentos
    • Schemas e tipos
    • IDs, paths e comandos
    • State transitions
    • Diferenças e patches relevantes

    Pode ser condensado

    • Documentação narrativa
    • Exploração antiga materializada
    • Logs após extração de erro
    • Explicações duplicadas
    • Histórico de hipóteses refutadas
    • Resultados extensos com artefato salvo

    AgentFold e abordagens de budget-aware context tratam o contexto como workspace que precisa ser reestruturado continuamente, em vez de um log append-only. [57][59][60]

    10 Tools, schemas e observações: o maior desperdício oculto

    Em agentes reais, o custo frequentemente vem mais de definições de ferramentas e resultados brutos que das instruções. A recomendação é manter poucas tools comuns carregadas e permitir discovery das demais.

    10.1 Tool discovery

    capabilities:
  loaded:
    - repository.read
    - repository.search
    - test.run
  discoverable:
    - browser.inspect
    - accessibility.scan
    - git.history
  denied:
    - production.deploy
    - secrets.read

    Anthropic documentou um caso em que converter MCP servers em uma interface navegável e carregar apenas definições necessárias reduziu 150.000 tokens para 2.000 tokens naquele workflow específico. O número não é uma expectativa universal, mas ilustra a magnitude potencial do overhead de schemas. [30]

    10.2 Filtragem determinística

    raw = tool.get_test_log()
result = {
  "exit_code": raw.exit_code,
  "failed_tests": extract_failed_tests(raw.stdout),
  "error_signatures": classify_errors(raw.stderr),
  "artifact_uri": save_full_log(raw)
}
return result

    O modelo recebe o resumo acionável e uma referência para o log completo. Isso reduz tokens sem destruir auditabilidade.

    10.3 Ferramenta é contrato, não documentação

    A interface precisa ter nomes não sobrepostos, argumentos tipados, side effects declarados, erros acionáveis e output com densidade alta. SWE-agent reforça que a ACI precisa ser desenhada para as habilidades do agente, enquanto Google ADK permite callbacks antes e depois de model/tool calls para observar ou bloquear ações. [5][35][37]

    11 Playbooks por papel

    11.1 Overseer

    mission:
  owns: [resultado-global, decomposição, delegação, integração, encerramento]
procedure:
  - understand-objective
  - classify-complexity-and-risk
  - construct-work-graph
  - delegate-with-boundaries
  - monitor-evidence
  - replan-when-needed
  - integrate
  - request-independent-validation
invariants:
  - do-not-spawn-unbounded-workers
  - do-not-accept-assertion-as-evidence
  - do-not-approve-own-governance-change

    A experiência da Anthropic indica que a delegação deve especificar objetivo, formato esperado, fontes/tools, fronteiras e esforço; instruções vagas causam duplicação e lacunas. [29]

    11.2 Router / gatekeeper

    mission:
  objective: Select an eligible route or abstain.
  doesNotOwn: [task-execution, implementation, policy-modification]
tools:
  allow: [capability-registry.read, project-profile.read, routing-history.read]
  deny: [repository.edit, shell.run, agent.create-unregistered]
output:
  schema: routing-decision/v2
control:
  abstainBelowConfidence: 0.70
  requireReasonCodes: true

    O router deve ter prompt pequeno, pouca memória, output estruturado e capacidade de abstenção. PerspectiveGap sugere avaliar tanto omissão quanto vazamento de informações de outros papéis. [45]

    11.3 Implementer

    mission:
  owns: [patch, testes-relacionados, evidência]
  doesNotOwn: [aprovação-final, requisitos, deploy]
procedure:
  - inspect-existing-patterns
  - map-criteria-to-changes-and-tests
  - implement-minimal-coherent-change
  - verify
  - handoff

    MASAI sugere especializar estratégias por subproblema, e AgentCoder mostra o valor de separar desenho e execução de testes do programador. [3][4]

    11.4 Reviewer

    mission:
  owns: [independent-findings]
  doesNotOwn: [silent-patch-rewrite]
tools:
  defaultMode: read-only
procedure:
  - reconstruct-intended-behavior
  - inspect-diff-and-impact-surface
  - attempt-to-refute-correctness
  - verify-tests-cover-risk
  - classify-findings-by-severity

    O reviewer precisa receber requisitos, diff, evidências e regras locais, mas não a cadeia de raciocínio privada do implementer.

    13 Workflow compiler e runtime pager

    O playbook compiler produz dois artefatos ligados: um manifesto efetivo e um workflow executável. Google ADK oferece sequências, loops e paralelismo determinísticos; LangGraph recomenda manter estado bruto e formatar prompts sob demanda, usando checkpointers para persistência e replay. [36][39][40]

    workflow:
  nodes:
    - route
    - explore
    - reproduce
    - implement
    - verify
    - review
  edges:
    - route -> explore
    - explore -> reproduce
    - reproduce -> implement
    - implement -> verify
    - verify.pass -> review
    - verify.fail -> implement
  termination:
    maxRepairLoops: 2
  gates:
    - before: protected-write
      require: approval

    13.1 Paging do frame ativo

    Compile, Then Page recomenda compilar primeiro e habilitar paging somente após avaliar se o modelo consegue seguir disciplina de estado; no estudo, modelos mais fracos foram prejudicados por alguns modos de guidance. [42]

    Recomendação: implemente três modos por modelo: full-program, active-frame + program-index e active-frame-only. Selecione por eval, não por preferência arquitetural.

    14 Segurança e governança

    14.1 Prompt não é enforcement

    Instruções naturais orientam comportamento; policies, callbacks, sandbox e tool gates limitam ações. AgentSpec propõe regras com trigger, predicate e enforcement; VIGIL estende a ideia para políticas temporais e value flows em eventos agent-tool. Google ADK recomenda callbacks/plugins para pre-validação de tool calls. [41][61][37]

    policy:
  id: protect-production
  trigger:
    tool: deploy
  predicate:
    environment: production
  enforce:
    requireApproval: release-manager

    14.2 Trust boundaries

    Documento de repositório não confiável
    Playbook assinado e versionado
    Skill de terceiro em quarentena
    Tool com side effects declarados
    Policy engine independente do modelo
    Reviewer sem poder de promoção
    Proposal agent ≠ approval authority
    Lockfile com provenance

    14.3 Regras de precedência

    1. Deny explícito vence allow e instruções naturais.
    2. Autoridade superior vence regra local quando há conflito de segurança.
    3. Regra mais específica vence apenas dentro do espaço permitido pela superior.
    4. Obrigação gera gate, não apenas lembrete textual.
    5. Conflito não resolvível falha a compilação.

    18 Anti-patterns

    God prompt

    Um Markdown universal com todas as práticas, tools e exceções.

    Persona teatral

    Biografia extensa sem mudança de contrato operacional.

    Concatenação cega

    global + role + skill + repo sem IR, precedência ou deduplicação.

    Full-context spawn

    Copiar toda a memória do overseer para cada worker.

    Tool catalog integral

    Carregar centenas de schemas em todo turno.

    Truncamento silencioso

    Cortar o fim do prompt quando o limite do vendor é atingido.

    Compressão de gramática

    Remover tokens de paths, IDs, code, schemas e tool calls.

    Policy textual

    Dizer “não faça” enquanto a tool continua disponível.

    Skill sem compatibilidade

    Práticas de framework sem versão e sem revalidação.

    Autoedição após uma falha

    Modificar playbook sem gerar eval, comparação e canary.

    B Apêndice — Esqueleto do compiler

    from dataclasses import dataclass
from typing import Any

@dataclass(frozen=True)
class CompilationContext:
    task: dict[str, Any]
    project: dict[str, Any]
    selected_role: str
    selected_model: str
    vendor: str

@dataclass(frozen=True)
class EffectivePlaybook:
    manifest: dict[str, Any]
    workflow: dict[str, Any]
    prompt_plan: dict[str, Any]
    provenance: list[str]

class PlaybookCompiler:
    def compile(self, context: CompilationContext) -> EffectivePlaybook:
        sources = self.registry.resolve(context)
        ast = self.parser.parse_all(sources)
        normalized = self.normalizer.normalize(ast)
        self.schema_validator.validate(normalized)
        compatible = self.compatibility.filter(normalized, context)
        merged = self.precedence.resolve(compatible)
        capabilities = self.capability_binder.bind(merged, context)
        policy = self.policy_engine.evaluate(context, capabilities)
        policy.raise_if_denied()
        workflow = self.workflow_compiler.compile(merged, policy)
        prompt_plan = self.context_compiler.plan(merged, workflow, context)
        manifest = self.lock_builder.build(
            context, merged, capabilities, policy, workflow, prompt_plan
        )
        return EffectivePlaybook(
            manifest=manifest,
            workflow=workflow,
            prompt_plan=prompt_plan,
            provenance=[s.uri for s in sources],
        )

    C Apêndice — Algoritmo de Spawn

    def compile_spawn_envelope(parent_state, delegated_task, profile, vendor):
    role_kernel = resolve_role_kernel(profile)
    task_capsule = build_task_capsule(delegated_task)

    relevant_state = select_state(
        parent_state,
        preserve=[
            "binding_decisions",
            "open_dependencies",
            "known_evidence",
            "active_risks",
        ],
        exclude=[
            "private_reasoning",
            "unrelated_workstreams",
            "expired_tool_outputs",
        ],
    )

    capabilities = bind_capabilities(
        profile=profile,
        task=delegated_task,
        common_tool_limit=3,
        defer_remaining=True,
    )

    envelope = assemble(
        static_prefix=role_kernel,
        dynamic_body=[task_capsule, relevant_state, capabilities.index],
        terminal_frame=[delegated_task.current_step,
                        delegated_task.return_contract],
    )

    envelope = reduce_to_budget(
        envelope,
        tokenizer=vendor.tokenizer,
        budget=vendor.spawn_budget,
        protected_sections=[
            "authority",
            "objective",
            "acceptance_criteria",
            "policies",
            "active_state",
            "output_contract",
        ],
    )

    validate_no_silent_truncation(envelope)
    return envelope
