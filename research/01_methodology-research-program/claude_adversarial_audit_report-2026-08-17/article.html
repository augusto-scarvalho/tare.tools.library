1. Escopo & Formulação do Problema

AUDIT_VERDICT: FAIL

As correções sanaram bem a lógica de tally / FSM fail-closed (RT-001), a validação de schema (RT-004) e a imutabilidade do DECISION.md (RT-007 parcial). Porém três bloqueadores permanecem abertos e uma regressão nova foi introduzida pela própria correção:

  • RT-002 continua 100% aberto: as flags --dangerously-bypass-approvals-and-sandbox / --dangerously-skip-permissions seguem presentes (linhas 340, 363, 380), e o endpoint /api/round_table/convene não tem autenticação. A "correção" foi apenas um delimitador textual <untrusted_proposal_data> — mitigação de prompt, não de segurança. Isso é RCE não autenticado em 3 máquinas.
  • RT-003 continua aberto na dimensão que importa: os locks são threading.Lock (in-process). O docstring afirma "Inter-process ... Mutex Lock" — falso. E mesmo in-process não há lease "caso ocupado".
  • Regressão nova (RT-N1, Crítica funcional): a verificação de hash de integridade (o "fix" do RT-007) transforma qualquer proposta com CRLF em um caso permanentemente quebrado (HELD_ERROR).

A suíte passa (7 testes) mas cobre só caminhos felizes das correções; nenhum teste exercita CRLF, re-init de caso não-terminal, concorrência real, crescimento de _CASE_LOCKS, ou injeção.

3. Novos Achados Adversários

🔴 RT-N1 — Crítica (funcional / disponibilidade)

Cenário de falsificação: Proposta com terminadores CRLF quebra o caso permanentemente.

  • init_round_table grava proposal_text via write_text_atomic (write_bytes → preserva \r\n) e computa sha256 sobre a string original com \r\n.
  • conduct_round relê via Path.read_text(encoding="utf-8") → newline=None (universal newlines) converte \r\n→\n → recomputa sha sobre \n → mismatch → raise ValueError("Integrity violation...") → except → status="HELD_ERROR", irrecuperável.
  • Falsifier concreto: init_round_table("RT-X","t","linha1\r\nlinha2") seguido de conduct_round("RT-X") lança integridade e trava o caso. Em Windows (CRLF é o default de qualquer editor/payload HTTP com \r\n), isso atinge o caminho feliz.

Código afetado: round_table_engine.py:439-444 (leitura) vs :239 (hash de init). Correção: Ler bytes crus e hashear bytes (v_file.read_bytes() / hashlib.sha256(raw)), ou abrir com newline="". Padronizar em uma única função _read_proposal() usada por init, conduct e finalize para eliminar o skew leitura↔escrita.

🔴 RT-N2 — Maior (integridade / imutabilidade)

Cenário: Re-inicialização de caso não-terminal-whitelisted sobrescreve a proposta e resseta a máquina.

  • O guard if existing.status in ("SEALED","COLLECTING","TALLY","APPROVED") não cobre HELD_UNAVAILABLE, HELD_ERROR, HELD_NO_CONVERGENCE, REJECTED, REVISION_REQUIRED.
  • Falsifier: dirija um caso a REJECTED (gera DECISION.md). Chame init_round_table(mesmo_id, novo_texto) → sucede, sobrescreve v001.md, cria state novo status=SEALED, round=1, apaga histórico de versões em state — mas DECISION.md (imutável) ainda diz REJECTED. Resultado: state/ledger/decision dessincronizados (exatamente o "ledger desincronizado" do mandato).

Código afetado: round_table_engine.py:234. Correção: Create-only real — bloquear se existing existe (qualquer status), OU se decision/DECISION.md existe. Colisão deve falhar fechada.

🟠 RT-N3 — Maior (exaustão de recursos / memory leak)

Cenário: Crescimento ilimitado de _CASE_LOCKS.

  • _get_case_lock insere um Lock por case_id e nunca remove. O espaço de case_id válido é enorme (^[A-Za-z0-9_\-]{3,64}$). Um cliente que bata em /convene ou /deliberate com IDs distintos (sem auth) faz o dict crescer sem limite no coordenador de longa duração → DoS por memória. Codex não viu porque os locks não existiam.

Código afetado: round_table_engine.py:49, 83-87. Correção: Limitar por número de casos ativos, ou usar weakref/GC de locks de casos terminais, ou trocar por lock interprocesso baseado em arquivo (filelock) por diretório de caso — o que também endereça RT-003.

🟠 RT-N4 — Menor (robustez de coerção)

Cenário: vote_data["strengths"] = "RCE" (string, não lista).

  • [str(s) for s in vote_data.get("strengths", [])] itera caracteres da string → ["R","C","E"]. Idem recommendations. confidence inválida vira 0.8 silenciosamente (viola "validação estrita" do RT-004).

Código afetado: round_table_engine.py:212, 214, 158-160. Correção: isinstance(list) guard antes de iterar; rejeitar (não coagir) confiança fora de faixa como schema inválido → HELD_UNAVAILABLE.

🟠 RT-N5 — Maior (concorrência residual, reforço do RT-003)

Cenário: Dois POST /api/round_table/deliberate para o mesmo cid.

  • Cada um dispara threading.Thread(run_full_deliberation). Como o lock não é mantido durante toda a run_full_deliberation, a Thread B adquire o lock nos intervalos entre operações da Thread A → duas deliberações intercaladas: dobro de invocações de CLI (custo/blast radius), seat_*.json e tally.json sobrescritos, transições de estado retrocedendo (APPROVED→COLLECTING). conduct_round não verifica se o caso já está terminal antes de rodar.

Código afetado: round_table_engine.py:427-450, 658-668; cluster_coordinator.py:2571-2576. Correção: Lease/CAS "caso ocupado" no início de run_full_deliberation; conduct_round deve recusar se status já é terminal (APPROVED/REJECTED/HELD_*).

🟡 RT-N6 — Menor (subprocess órfão / Windows)

Timeout mata o filho direto (codex/claude.cmd/agy), mas os netos (node/python reais) sobrevivem sem job object → vazamento de processos ao longo de muitas deliberações. Reforça RT-008. Correção: criar grupo/job (CREATE_NEW_PROCESS_GROUP + taskkill /T, ou psutil para matar a árvore).

4. Engenharia de Sistemas & Resiliência Distribuída

  • Modelo de concorrência inadequado ao topo distribuído declarado. O sistema explicitamente tem 2 PCs + nós remotos + CLIs + coordenador HTTP, mas a exclusão mútua é threading.Lock em memória de um processo. Não há single-writer, lease interprocesso, nem CAS. A afirmação de "Inter-process Mutex" no cabeçalho é falsa e perigosa (dá falsa confiança). Para o alvo declarado, o lock precisa ser por-arquivo no diretório do caso (ex.: filelock/O_EXCL lock file), que também resolve RT-N3.
  • Ledger não é fonte de verdade transacional. save_state (replace atômico) + append_ledger (append não-fsync) são operações independentes. Não há protocolo de commit; crash entre as duas dessincroniza. O os.replace garante atomicidade por arquivo, não atomicidade da transição (state+ledger+artefato). RT-006 segue conceitualmente aberto.
  • Integridade por hash frágil. O único ponto de verificação (RT-N1) usa uma leitura com normalização de newline diferente da escrita → o mecanismo de integridade falha inseguro para o sistema (brick), não fecha de forma controlada. Hash deve ser sempre sobre bytes canônicos.
  • Autoridade determinística vs probabilística mal isolada (North Star). A decisão determinística (FSM/tally) está OK, mas ela depende de saída de LLMs executados com autoridade máxima e sem sandbox sobre dados não confiáveis. A fronteira probabilística→determinística é atravessada por RCE (RT-002): a camada probabilística pode adulterar a máquina que hospeda a camada determinística. Isolamento inexistente.

4. Limitações & Ameaças à Validade

NÃO PRONTO PARA ROLLOUT. Bloqueadores obrigatórios antes de qualquer landing:

  1. RT-002: remover flags perigosas; sandbox com allowlist e dir restrito; autenticar /convene e /deliberate.
  2. RT-N1: hashear bytes canônicos (elimina o brick de CRLF).
  3. RT-N2: init verdadeiramente create-only (bloquear qualquer caso existente).
  4. RT-003/RT-N5: lock interprocesso por caso + lease "ocupado" + guarda de estado terminal em conduct_round.
  5. RT-N3: limitar/coletar _CASE_LOCKS.
  6. RT-008/RT-N6: limite de bytes na captura, deadline global por caso, kill de árvore de processos.

Testes negativos ausentes a adicionar: CRLF→integridade, re-init de caso terminal, strengths string, deliberação concorrente, crescimento de locks, timeout com órfãos.

Achados que o Codex acertou e foram bem fechados: RT-001 e RT-004 estão sólidos; RT-005/RT-007 melhoraram mas ficaram com as brechas residuais acima. Nenhuma correção do Codex piorou a segurança, mas a correção de RT-007 introduziu a regressão RT-N1.

Não alterei nenhum arquivo — auditoria somente leitura, como pedido. Se quiser, aplico os fixes de RT-N1 (hash sobre bytes) e RT-N2 (init create-only) num diff mínimo — são as duas correções de maior impacto por menor linha.
