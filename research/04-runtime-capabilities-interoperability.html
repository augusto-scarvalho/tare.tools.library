Runtime, Capabilities, Isolation & Interoperability

Como usar CLIs, HTTP endpoints, MCP, A2A, sandboxes, durable runtimes e infraestrutura externa sem permitir que mecanismos definam a ontologia do tare.tools.

1. Tese consolidada

tare owns meaning; external systems provide mechanisms, projections, attestations or qualified backends.

Interoperabilidade não é “suportar protocolos”. É preservar — ou declarar explicitamente a perda de — identidade, authority, causality, lifecycle, artifacts e evidence quando um objeto canônico cruza uma boundary.

2. Três classes de runtime

  • vendor-local: vendor possui agent loop; tare adapta, governa e observa;
  • harness-owned: provider fornece inference; tare fornece agência via HarnessAgentRuntime/ModelProviderAdapter;
  • vendor-remote: runtime managed/remoto com lifecycle próprio.

Conformance é externa. Exigir implementação interna idêntica destruiria a vantagem do modelo multi-vendor e impediria runtimes locais/consumer GPU de serem cidadãos de primeira classe.

3. Capability/Effect é boundary arquitetural

Filesystem, shell, Git, browser, databases, MCP, artifacts e serviços externos convergem semanticamente em capabilities/effects. Models propõem; Authority autoriza; capability infrastructure executa; receipts sustentam claims.

Sandbox é backend de isolation/lease, não fonte de autoridade. A arqueologia Kimi/Antigravity mostrou empiricamente que declared/configured capability parity ≠ runtime-loaded/enforced/effective parity. Qualificação precisa chegar ao efeito observável, não parar em config.

4. Boundary projection e smallest sufficient view

O runtime/protocolo recebe somente o necessário: contexto relevante, capabilities elegíveis, ceiling de autoridade delegada, artifact refs e metadata/version pins. `ExecutionBinding` é o seam natural para conectar candidate, runtime owner, adapter/provider versions, qualification snapshot e authority refs.

  • MCP: capability/resource protocol backend; não internal bus.
  • A2A: boundary de agentes independentes/opaque; não runtime interno tare.
  • CLI: transport/runtime surface para vendor-local.
  • HTTP inference: natural para harness-owned runtime.
  • OTel: projection/sensor; spans não são EffectReceipt.

5. Technology rings e semantic exit test

Ring 0 — tare canonical semantics
Ring 1 — qualified mechanics: Git, DB, artifact store, durable runtime, sandbox
Ring 2 — projections/interchange: OTel, OpenLineage, W3C PROV, SLSA/in-toto
Ring 3 — labs: MLflow, Dagger, GUAC, Jujutsu/lakeFS spikes

Para qualquer dependency, perguntar: “se removê-la amanhã, o que perdemos?” Se a resposta for performance/convenience, boundary saudável. Se perdermos a capacidade de interpretar Task/Authority/Evidence, houve semantic capture.

OCI/ORAS é candidato interessante para payloads/attestations; Temporal, Restate e DBOS são candidatos de durable execution; SPIFFE/SPIRE pode autenticar workload; Cedar/OpenFGA podem avaliar policy/relations. Nenhum deles deve mintar Permit, Workflow truth ou OutcomeEvidence por conta própria.

6. Windows/local-first é constraint arquitetural

Qualification precisa incluir Windows-native e POSIX/CI. IDs canônicos não podem depender de path syntax, PID ou hostname. Infra pesada de federation deve ser adiada até necessidade real; local modes e optional backends preservam experimentabilidade em workstation/consumer GPU.

7. ADOPT / ADAPT / RETIRE / OPEN

ADOPT

runtime ownership; capability-mediated effects; protocol/version pinning; qualification progression; semantic exit test; smallest sufficient view.

ADAPT

MCP/A2A/OTel/SPIFFE/SLSA como adapters/projections/attestations; sandbox/process supervisors como substrate backends.

RETIRE

MCP as architecture boundary; A2A internal bus; protocol-specific authority/evidence types; config-only “sandbox proof”; provider==runtime identity.

OPEN

trusted invocation seam; filesystem confinement proof; federation identity; semantic-fidelity metrics; tare↔tare compatibility profile; artifact transfer.

8. Qualification Pack mínimo

  1. semantic conformance e round-trip/projection parity;
  2. failure/degraded modes e observer staleness;
  3. version/upgrade drift;
  4. offline/local behavior;
  5. Windows/POSIX matrix;
  6. security/trust boundary;
  7. replaceability/rollback;
  8. evidence de enforcement/effect, não somente declaração.

Absorve CLI/endpoints, Kimi runtime archaeology, sandbox/process-control studies, protocols/interoperability, resource/container research e technology landscapes de lineage/reconstructability.
