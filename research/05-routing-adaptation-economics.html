Routing, Adaptation, Economics & Resources

Escolher ExecutionBinding sob policy, availability, evidence, custo e delayed outcomes sem permitir que reputation ou economics virem autoridade.

1. Tese consolidada

Routing é constrained decision-making, não leaderboard selection. Primeiro elimina-se o que não é autorizado/elegível/capable/disponível; somente depois utility, reputation, economics e exploração podem ordenar candidatos.

2. Ordem conceitual

Policy / Authority
 → eligibility
 → capability fit
 → runtime availability / suppression
 → budgets / commercial lanes / quota pools
 → project-local predicted utility
 → bounded exploration if permitted
 → RouteDecision persisted before spawn
 → execution → outcome → attribution

Essa ordem elimina um erro recorrente do corpus antigo: deixar “melhor modelo” ou “vendor com crédito disponível” dirigir o sistema antes de verificar autoridade/capability.

3. Candidate é mais que model name

`Model`, `Provider`, `Provider Route`, `Runtime`, `Runtime Owner` e `Commercial Lane` são dimensões distintas. Para local models, quantization/config/runtime podem mudar performance e capability materialmente; portanto um CandidateKey pode precisar representar configuração qualificada sem colapsar tudo em provider/model.

Static benchmark score não transfere automaticamente para derivative, quantization ou runtime. QualificationSnapshot e evidence epoch precisam acompanhar a decisão.

4. De router estático para política temporal

As pesquisas mais recentes sugerem que early execution trajectory contém signal que task text não possui. Isso apoia routing/re-routing temporal, mas com limites: propensities/context devem ser persistidos durante experimentação para permitir off-policy evaluation, e exploration nunca contorna Authority.

Global priors ajudam cold start; project-local posteriors devem dominar quando há evidence suficiente. Transfer cross-project exige applicability/transportability e precisa medir negative transfer. Evidence stale deve decair/requalificar.

5. Economics e resources

Custo não é somente token price. O objetivo operacional mais útil é cost-to-trust: inference + retries + validation + human interruption + latency + scarce resources até um outcome defensável.

Quota pool/commercial lane não é identidade de provider. Local GPU/RAM/VRAM e human attention são recursos concorrentes e devem ser tratados como constraints/telemetry operacionais, não como authority.

6. Evidence loop

RouteDecision deve existir antes do spawn e carregar snapshot/context suficiente para atribuição posterior. OutcomeEvidence pode chegar tarde; reputation é materialized view desse evidence, não side service capaz de “aprovar” work.

O hot path usa snapshots compactos. O warm path atualiza qualification/reputation. O cold path faz análise causal, delayed outcomes e experimentação. Separar esses tempos reduz coupling e permite replay.

7. ADOPT / ADAPT / RETIRE / OPEN

ADOPT

eligibility-first; simple baselines; decision-before-spawn; project-local evidence; runtime suppression overlays; OPE/shadow; cost-to-trust.

ADAPT

model picker → temporal routing policy; vendor credits → quota/commercial lane; utility scalar → constrained multi-objective decision.

RETIRE

reputation before policy; provider==runtime; leaderboard inheritance; router self-validating improvement; single global score for all projects.

OPEN

exploration policy; delayed route regret; OPE instrumentation; systemic resource-risk aggregation; CandidateKey dimensions for local inference.

8. Programa de falsificação

  1. Simple baseline treasury: random/cheapest/strongest/static heuristic versus learned policy.
  2. Shadow OPE: persist propensities and compare counterfactual estimates with later canary outcomes.
  3. Project-local vs global: hierarchical evaluation em project archetypes + held-out projects, medindo negative transfer.
  4. Trajectory routing: prompt-only versus early-experience routing, custo de obter signal incluído.
  5. Resource scheduler: tokens/s versus cost-to-trust/human interruption como objective.
