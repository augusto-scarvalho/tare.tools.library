# Project / Workspace Admission & Adoption — preservation edition

**Status:** RESEARCH / PROPOSED integration seam.

## Why this survives separately

Project is not just a repository path. It is the namespace in which policy, evidence, resources, workflows, qualification, memory and learning acquire applicability. Collapsing Project admission into Agent OS foundations loses the lifecycle problem of bringing an incumbent repository/system under governance.

## Research problem

How does tare.tools discover, model and progressively govern an existing Project without assuming it was born tare-native?

## Key distinctions

- observed repository/system facts versus declared desired state;
- Project identity versus revision/snapshot;
- adoption/readiness versus implementation completeness;
- read-only discovery versus authority-bearing changes;
- project-local evidence versus platform/global priors.

## Migration pattern

1. Discover read-only.
2. Pin identity/revision and evidence sources.
3. Materialize a Project model/projection.
4. Assess capability, policy and assurance gaps.
5. Introduce adapters and compatibility contracts.
6. Shadow governance before enforcement.
7. Promote vertical slices with rollback.

## Cross-links

Feeds Workflow planning, Candidate eligibility, Context compilation and cross-project learning. Canonical Lineage must be able to say which Project revision a work/effect/evidence item refers to.
