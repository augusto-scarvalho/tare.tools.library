Agent OS Foundations & Canonical Spine

Do harness multi-vendor governado a um Agent Operating System em user space sem criar um superagente, um kernel vendor-specific ou um segundo sistema operacional.

RESEARCHNorth-Star directedstable incumbent

1. Tese consolidada

tare.tools é mais bem compreendido como um substrato de governança e execução em user space: probabilístico na interpretação, dinâmico no planejamento, durável na execução, determinístico na autoridade, capability-mediated nos efeitos, evidence-driven no aprendizado e conservador na autoevolução.

A analogia com OS é útil apenas quando força clareza de ownership, lifecycle, isolation, resources, capabilities e observability. Ela deixa de ser útil quando incentiva reimplementar kernel/device abstractions ou transformar todo conceito em uma nova “Plane”. O Agent OS deve possuir significado canônico; o host OS, vendors e frameworks continuam possuindo mecanismos físicos.

2. O problema que sobreviveu à arqueologia

Os estudos de julho perceberam corretamente que “prompt orchestration” era insuficiente, mas misturavam agents, workflows, providers, sandboxes, policies e UX porque os boundaries ainda estavam emergindo. O refinamento posterior mostra que o desafio não é adicionar um componente centralizador: é fazer subsistemas heterogêneos convergirem em poucos contratos externos e numa única disciplina de autoridade/evidência.

Daí surge a regra anti-Frankenstein: um mecanismo externo só é saudável se o tare.tools continuar capaz de interpretar seu próprio Work, Authority, Effect e Evidence depois de removê-lo.

5. Findings que sobrevivem

  • Stable incumbent é ativo epistemológico. Compatibilidade deve ser provada contra comportamento histórico antes de removê-lo.
  • Runtime ownership é plural. Vendor-local, harness-owned e vendor-remote não precisam ter loop interno idêntico; precisam convergir externamente.
  • Authority before intelligence. Model, routing, memory e reputation jamais concedem autoridade.
  • Capability é boundary de efeito, não MCP. MCP é um protocolo/backend possível.
  • Evidence precisa sobreviver a vendor/framework turnover. Telemetry e logs são sinais; receipts/provenance sustentam claims.
  • Architecture epoch é necessário como interpretação histórica, ainda que possa começar como metadata/view e não nova primitive.

6. ADOPT / ADAPT / RETIRE / OPEN

ADOPT

user-space Agent OS; Strangler/Branch by Abstraction; runtime ownership; capability-mediated effects; canonical IDs/provenance; backend qualification.

ADAPT

agent/overseer taxonomies → runtime/workflow roles; tool brokers → capability adapters; “memory” → lifecycle-scoped views plus durable knowledge.

RETIRE

super-agent framing; provider-specific kernel branches; prompt text as enforcement; per-vendor ontologies; research docs acting as architecture authority.

OPEN

architecture-epoch representation; root/constitutional authority; Project inventory semantics; cross-version compatibility treasury.

7. O que falsificaria esta direção

  1. Um vertical slice em que adapters/canonical contracts custem mais complexidade e reduzam confiabilidade versus um desenho vendor-specific, sem benefício de replaceability.
  2. Falha em reproduzir comportamento do incumbent sob um contract canônico sem expor detalhes internos de vendor.
  3. Evidência de que a spine precisa de um novo owner sem equivalente canônico; nesse caso o gap deve ser demonstrado por golden queries/BDD antes da primitive.
