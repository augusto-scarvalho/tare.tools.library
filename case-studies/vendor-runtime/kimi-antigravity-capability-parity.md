# Kimi / Antigravity Runtime Archaeology — capability parity case study

**Status:** EMPIRICAL CASE STUDY; historical CURRENT evidence must remain epoch-scoped.

## Why it matters

Static AP/repo-health/audit/doctor checks appeared green while the real Antigravity CLI loaded **zero hooks**. Runtime exercise exposed schema mismatch, then raw smoke/named-hook corrections proved progressively stronger capability evidence.

## Surviving finding

**static capability parity ≠ runtime capability parity.** A useful qualification ladder emerged:

`DECLARED → RENDERED/CONFIGURED → LOADABLE → ENFORCED → EFFECTIVE`.

This ladder is a research/qualification model, not automatically a canonical enum.

## Architectural consequences

- adapters belong at vendor boundaries;
- vendor-local runtime needs actual load/enforcement/effect evidence;
- configured hooks/tools are not proof of confinement;
- process/workspace/sandbox containment remains tare-owned responsibility where required;
- exact candidate-tree evidence matters;
- readiness is vectorial, not one boolean.

## Negative evidence preserved

False green itself is valuable. The case should be reused to design qualification packs and to reject claims like “feature supported” when only configuration exists.
