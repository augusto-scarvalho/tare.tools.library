A pesquisa antiga chegava aproximadamente aqui:

```text id="61ktj5"

    ↓

    ↓
ToolBroker
    ↓

    ↓
```

Esse desenho foi extremamente útil para descobrir **como as CLIs funcionam**, mas não deve virar a arquitetura final do tare.tools.

A leitura atual é:

```text id="pgc0py"
EXPERIENCE
TUI · REPL · IDE · API
        │
        │ typed intents / approvals / steering
        ▼
PROJECT / IDENTITY / AUTHORITY / POLICY
        │
        ▼
WORKFLOW
        │ RouteIntent
        ▼
ROUTING & ADAPTATION
        │ RouteDecision

        │
 ┌──────┼────────────────┐
 ▼      ▼                ▼
vendor  harness-owned    vendor-remote

        │

        │
```

Essa arquitetura coincide muito melhor com o North Star atual, que explicitamente trata o Agent OS como um user-space substrate, e não como substituto de Windows/Linux. fileciteturn4file0

## O que a pesquisa de runtimes ganhou com o recentramento

A investigação de vendors continua extremamente valiosa. Na verdade, fica **mais útil**, porque deixa de procurar um “runtime vencedor”.

O que aprendemos com Codex, Claude, Kimi, Gemini, Antigravity, Copilot, Kiro, Qwen, Mistral, OpenHands, Hermes, Herdr, OpenRig etc. passa a alimentar uma matriz do tipo:

```text id="cj04xs"
padrão observado
    ↓
canonical equivalent?
    ↓
bounded-context owner
    ↓
CURRENT / TARGET / PROPOSED / RESEARCH
    ↓
ADOPT / ADAPT / RETIRE / OPEN
    ↓
contract
    ↓
qualification/evidence
```

Alguns exemplos importantes:

| Ideia histórica | Agora |
|---|---|
| `ToolBroker` | **RETIRE como primitive nova**; convergir para `CapabilityBroker` |
| tool call | `ActionRequest` |
| aprovação | decisão Authority/Policy projetada à UI |
| resultado da tool | `EffectReceipt` + resultado semântico |
| workspace | `WorkspaceLease` |
| `AgentEngine` genérico | runtime implementation, não novo kernel |
| vendor CLI executor | `runtimeOwner=vendor-local` |
| endpoint com nosso loop | `runtimeOwner=harness-owned` |
| managed agent | `runtimeOwner=vendor-remote` |
| wire log | `HarnessEvent` + causal IDs + Evidence |
| process scraping / abtop | sensor do Evidence Plane, nunca autoridade |
| Herdr/OpenRig | adapters/backends para vendor-local runtime |
| GoalContract | composição sobre Task/Workflow/claims, não segundo goal system |
| model/provider compatibility | QualificationSnapshot, não booleano |

Esse é talvez o maior ganho da atualização: **paramos de colecionar boas abstrações dos vendors como candidatas automáticas a primitives próprias**.

## O que muda no TUI/REPL

A pesquisa de UX já tinha chegado a uma boa tese:

> **chat-first, control-on-demand.**

Ela continua válida. Mas agora eu a expandi para:

> **chat-first, progressive operational disclosure, control-on-demand.**

Ou seja, normalmente o usuário vê conversa, trabalho atual, atividade crítica, composer e estado essencial. A interface ganha densidade quando **risco, incerteza, concorrência ou necessidade de intervenção aumentam**.

A consequência mais importante é ownership:

| Coisa mostrada | Quem realmente possui |
|---|---|
| modelo ativo | Routing + Runtime |
| provider | ExecutionBinding / Runtime |
| approval | Authority/Policy |
| tool/capability | Capability Plane |
| sessão/run | Durable Runtime |
| contexto/memória | Memory/Context |
| diff/artifact | Artifact + Assurance |
| subagentes | Workflow + Delegation + Runtime |
| custo/quotas | Economics/Resources |
| status de projeto | Project Operating Model |
| evidências | Evidence/Assurance |
| evolução | Evolution Control |

A TUI **não inventa** esses estados. Ela os projeta.

Isso corrige um drift sutil de algumas SPECs anteriores nas quais coisas como `UIEvent`, `ModelBinding` e `ApprovalTicket` quase pareciam objetos de domínio da própria interface.

## Novas telas que aparecem naturalmente quando pensamos em Agent OS

Uma descoberta importante do recentramento é que a nossa TUI futura não serve apenas para “coding agent chat”.

Ela provavelmente precisará, progressivamente, de superfícies para:

```text id="rzoya7"
Project Admission
Authority / Permits
Evidence / Assurance
Runtime Fleet
Resource / Economics
Memory provenance
Incident / Recovery
Evolution Review
Qualification
Workflow / topology
```

Mas isso **não significa colocar dez painéis permanentemente na tela**.

A pesquisa anterior sobre Gemini, Qwen, Codex, Kiro, OpenCode, Claude e Kimi continua sugerindo que esse seria um erro.

A solução permanece:

```text id="p1t2qc"
frequente + importante
        → persistent compact state

temporariamente ativo
        → activity strip

pesquisável
        → picker / command palette

profundo
        → inspector

bloqueante / authority-sensitive
        → modal durable dialog

diagnóstico
        → dedicated view

automação / accessibility
        → Stable REPL
```

## Alguns novos ramos que acrescentei

A busca complementar encontrou linhas recentes que se encaixam muito bem nessa mudança.

**Plan-centric steering.** Plover mostra uma abordagem em que o plano permanece visível e o humano pode reparar partes localizadas da execução, em vez de reiniciar tudo ou ler traces enormes. Isso se conecta diretamente a Workflow/GraphPatch + Experience. ([arxiv.org](https://arxiv.org/html/2607.15193v1?utm_source=chatgpt.com))

**Protocolos de colaboração humano–agente.** CHAP argumenta que prompts e orchestration frameworks não definem sozinhos o contrato de colaboração e propõe um vocabulário wire-level para esses eventos. É particularmente interessante para steering/clarifications/handoffs como **protocol adapter**, não como nova authority layer. ([arxiv.org](https://arxiv.org/html/2606.09751v1?utm_source=chatgpt.com))

**Operator comprehensibility.** Trabalhos recentes sobre Agent Operating Systems colocam compreensibilidade, auditabilidade e deterministic enforcement entre critérios centrais do sistema, o que sugere tratarmos a qualidade da TUI também como propriedade de safety/governance. ([arxiv.org](https://arxiv.org/abs/2606.01508?utm_source=chatgpt.com))

**AgentGUI e supervisão de long-running agents.** Um trabalho de julho de 2026 reporta redução estatisticamente significativa no tempo necessário para encontrar elementos importantes em traces quando eles são apresentados por uma interface dedicada. O caminho promissor para nós é testar causal summaries e evidence navigation — não simplesmente mostrar mais logs. ([arxiv.org](https://arxiv.org/abs/2607.26300?utm_source=chatgpt.com))

**Terminal como paradigma de colaboração.** Um trabalho de 2026 argumenta que a força do terminal vem de compatibilidade representacional, transparência das ações e baixa barreira entre humano e agente. Isso é uma boa justificativa teórica para manter o Stable REPL como superfície de primeira classe, não como fallback pobre da GUI. ([arxiv.org](https://arxiv.org/abs/2603.10664?utm_source=chatgpt.com))

**Agent-native computer interfaces.** CLI-Anything reforça a ideia de interfaces estruturadas, comandos explícitos e feedback determinístico em vez de obrigar agentes a imitar interações humanas visuais. Isso abre um ramo interessante: o Stable REPL do tare.tools pode ser simultaneamente uma ótima interface humana **e** uma superfície machine-consumable, desde que não se transforme em um segundo protocolo ad hoc. ([arxiv.org](https://arxiv.org/abs/2606.03854?utm_source=chatgpt.com))

### Minha síntese final desta conversa

> **A primeira metade deste chat descobriu como separar inferência de agência e como acomodar runtimes heterogêneos sem perder tools, estado, sandbox, approvals e durabilidade. A segunda descobriu como tornar esse sistema operável por humanos no terminal. A North Star atual une os dois: runtimes tornam-se implementações/adapters de um kernel vendor-neutral; TUI e REPL tornam-se projeções do Experience Plane. Authority, Project truth, effects, evidence, routing e evolution permanecem fora de ambos, em bounded contexts canônicos.**

Essa mudança não poda as ideias anteriores. Ela elimina justamente o risco de elas virarem **sistemas paralelos** ao Agent OS.
