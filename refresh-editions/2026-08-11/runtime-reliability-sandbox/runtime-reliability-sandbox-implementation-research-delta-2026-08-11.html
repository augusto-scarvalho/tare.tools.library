4. CURRENT × TARGET gap

CURRENT is evidence-limited in this refresh because the dirty working repository is not mounted. The 2026-08-05 snapshot and later project handoffs prove historical mechanisms and specific falsifications, not today's entire implementation.

TARGET follows the North Star summarized in [P01]/[P02]. The practical gap for this lineage is: Build a runtime conformance model around canonical external contracts rather than identical internals. Every side-effecting capability should declare recovery-relevant semantics (idempotent, deduplicatable, reconcilable, compensatable, cancellable, independently observable, irreversible) as qualified metadata where justified. Preserve `AMBIGUOUS → RECONCILE` as a first-class state in effect handling. Qualify sandbox backends through adversarial escape/confinement suites, including Windows as first-class and POSIX/CI parity. Do not mark strict proof eligible until judge provenance, invocation trust and confinement are independently established.

6. Contract invariants

  1. Authority is evaluated before any optimization or effect.
  2. Execution identity and candidate identity are pinned before work begins.
  3. Effects produce receipts/observations that distinguish request, attempt, observed postcondition and uncertainty.
  4. Evidence remains append-only/provenanced; derived views are rebuildable.
  5. Protocol/vendor/runtime metadata stops at adapters and ExecutionBinding-like seams.
  6. Historical behavior remains available behind compatibility adapters until parity and rollback criteria pass.

8. Strangler migration slices

  1. S0 — observe: add read-only instrumentation/projection around incumbent behavior.
  2. S1 — canonical adapter: map incumbent behavior to existing canonical contracts without changing semantics.
  3. S2 — parity: run incumbent and candidate path against the same frozen subjects; preserve negative evidence.
  4. S3 — shadow: compute new decision/result but do not grant effects or promotion authority.
  5. S4 — low-risk canary: enable only where rollback/reconciliation are explicit.
  6. S5 — expand: increase coverage after evidence sufficiency and Windows/POSIX parity.
  7. S6 — retire legacy: delete only after compatibility/deprecation criteria and replay treasury pass.

9. Candidate BDD scenarios

  • Given/When/Then: retry waits for reconciliation when duplicate unsafe.
  • Given/When/Then: sandbox configuration alone does not satisfy confinement proof.
  • Given/When/Then: stale lease/authority prevents commit.

10. Evidence and gates

  • Unit/contract tests for pure semantics.
  • Scenario parity against historical incumbent behavior.
  • Negative/adversarial tests for authority bypass and evidence fabrication.
  • Replay from frozen candidate identities.
  • Windows-native + POSIX/CI conformance where runtime/filesystem/process semantics are implicated.
  • Performance gates should report cost/latency/resource deltas separately from correctness.
  • Promotion requires independent evidence appropriate to risk; agent self-report is never sufficient.

11. Candidate Implementation Packets

  1. Packet A — Reconciliation only: map semantic roles above to current repo types/fields and produce a Gap Registry. No behavior change.
  2. Packet B — Read-only projection/instrumentation: expose missing evidence using adapters around incumbent behavior.
  3. Packet C — One vertical semantic slice: implement the smallest gap with parity + rollback.
  4. Packet D — Qualification experiment: compare old/new path under frozen tasks and independent validation.

12. Transverse risks and explicit non-goals

  • No greenfield rewrite.
  • No new vendor-specific subsystem in core.
  • No promotion based on research freshness alone.
  • No erosion of mobile/Windows workflows or POSIX CI.
  • No observer/telemetry backend becoming canonical Authority or Evidence by accident.
  • No coupling of local consumer-GPU runtimes to cloud-only assumptions.
